# Architecture

Trust, memory, and dreaming boundaries are described in [memory.md](memory.md). User-authored skill storage, run selection, isolated building, approval, privacy, and budget contracts are described in [skills.md](skills.md).

MatoLoop is a provider-neutral monorepo. FastAPI provides REST and SSE interfaces; the Quasar PWA consumes only this API.

## Layers

- API: HTTP contracts, authentication, and dependency injection
- Services: transactions and application logic
- Agent: provider-neutral model and tool loop plus host policies
- Execution: outbound MatoLoop Agents for selected filesystem, process, and static local-integration operations
- Providers: replaceable LLM and search transports
- Memory: current-session context plus audience-filtered durable and owner-scoped prior-session retrieval
- Embedding: local Infinity transport and asynchronous durable-memory and episode vectors
- Persistence: SQLAlchemy models, Alembic migrations, and settings documents
- Frontend: presentation, user interaction, and localization

MatoLoop is a modular monolith, not a collection of internal microservices. Backend API
routes retain HTTP schemas, dependencies, status codes, and controlled error mapping. The
`sessions` and provider settings services own their application workflows, while the API
workspace service owns reusable HTTP context and dispatch rules. Transaction and
filesystem compensation boundaries stay in those application services. Provider adapters,
the agent runtime, integrations, and MatoLoop Agent operations expose explicit module-level
contracts and do not depend on FastAPI routes.

The agent package separates research projection, memory preparation, and tool argument
contracts from the central runtime and registry while preserving one provider-neutral loop.
SQLAlchemy models are split by aggregate and re-exported through `models`; Alembic still sees
one metadata graph. The frontend keeps Pinia stores as stable feature facades and moves
cohesive state helpers, route metadata, and styles under `features`, `app`, and `shared`.
The standalone implementation lives in `apps/matoloop-agent` under the `matoloop_agent`
package. It has no backend package or database dependency.

## Authentication and Ownership Boundary

`UserAccount` is the stable internal principal and is independent of a login method. The first local setup account is an active administrator; upgrades promote the earliest existing account. Administrators can create local accounts, reset passwords, activate or deactivate users, assign administrator status, and delete deactivated users. The last active administrator is protected. The role grants account administration and instance-settings mutation only: every content API still applies the authenticated owner's ID, there is no impersonation path, and an administrator cannot inspect another user's sessions, messages, files, memories, credentials, personal settings, approvals, or MatoLoop Agents.

Local username and password authentication is currently the only implemented provider. Usernames retain their entered spelling but are compared and constrained case-insensitively. `AuthenticationProvider` and `UserAuthIdentity` persist the foundation for external login providers, and provider subjects are unique only within a provider. No external provider transport, callback route, or login/linking UI exists yet. A future provider may independently enable just-in-time creation of a non-administrator account. Existing authenticated users must self-link explicitly; MatoLoop never links accounts from a matching username or other mutable profile value, and unlinking cannot remove the final login method.

Sessions own messages, runs, approvals, grants, notifications, and internal session storage. Optional projects group owner-bound sessions and own shared project files, plans, and coding executions. Memories, credentials, personal settings, and `ExecutionAgent` records carry the same user boundary. Workspaces are ordinary absolute paths externally owned by MatoLoop Agents. Owner checks apply in services and queries before trust or retrieval filtering. Instance-scoped providers, models, integrations, integration resources, and tool policies are deliberately shared configuration and are not another user's personal content.

## Projects and Coding Boundary

Projects are optional owner-bound session groups; standalone sessions remain valid. A project may connect one personal OpenCode binding from the Control Center containing only the integration ID, remote project identity, relative workspace identity, separate analysis and execution model keys with optional model-specific variants, and queue pause state. The binding may change or disconnect until the first plan is saved; model selections, variants, and queue pause state reset when it changes. Remote absolute paths remain backend-only, and OpenCode is a backend integration rather than an LLM provider or MatoLoop Agent.

OpenCode performs read-only repository analysis. The MatoLoop agent uses those findings to author the canonical persistent Markdown plan. Plan creation snapshots the configured analysis model and variant; enqueueing snapshots the exact plan revision, text, execution model, variant, and working directory. A null variant delegates to the OpenCode model default, while an explicit variant must still be advertised by that model before dispatch. Executions are persistent FIFO records with at most one active execution per project. External OpenCode activity pauses the queue; restart or an uncertain post-dispatch failure records `outcome_unknown` and is never replayed automatically. OpenCode permission requests remain visible and require `once`, `always`, or `reject` before execution continues.

## Chat Submission Boundary

The browser keeps unsent chat submissions and their attachments in an owner-scoped IndexedDB outbox and drains each session in FIFO order when no run, approval, question, or conflicting mutation blocks it. Every entry has one browser-generated UUID that is reused as its requested `AgentRun` ID. Session creation and message endpoints return the canonical persisted session, input message, and run when that owned UUID already exists; a UUID tied to another owner or session remains a conflict. This makes retries after an unknown HTTP outcome safe without turning persisted run state into a resumable backend execution queue. Failed sends remain paused in the browser until the user retries, and logout or account replacement clears the previous owner's outbox before reloading.

## PWA and Push Boundary

The production frontend is an installable PWA, but its service worker has no fetch handler and no offline application cache. The stable `/sw.js`, manifest, and HTML entry point are served without caching; updates are checked at startup, when the app becomes visible, and at most hourly without forcing a page reload. Web Push permission is requested only after a direct user action. Browser subscriptions are owner- and device-bound, their endpoint and key material are encrypted with the credential key, and delivery accepts only configured exact HTTPS push-service origins without redirects. Re-registering a browser endpoint atomically transfers it to the currently authenticated owner so an expired prior login cannot keep receiving notifications on a shared browser. Producers dispatch versioned, host-validated payloads only after committing canonical notifications, messages, approvals, or questions. Delivery is best effort and can never roll back those records; stale subscriptions are removed only after a terminal push-service response.

## Configuration Boundaries

Bootstrap and infrastructure values come from environment variables. Operational settings are stored as typed Pydantic documents in the PostgreSQL `settings` table.

Additive settings fields have Pydantic defaults. Settings documents declare instance or user scope. Instance documents use `settings.user_id IS NULL`; user-scoped documents are loaded and stored with an explicit `user_id`. Partial unique indexes enforce the two namespaces separately. Background processing derives user scope from persistent session ownership and never uses an implicit request user. API keys and OAuth tokens are referenced by ID from the separate `credentials` table instead of being stored in settings JSON. Credentials carry the same nullable owner convention: null means an intentionally shared instance credential, while a user ID means personal and owner-only. Credential payloads are encrypted; the Fernet key is created under `/data/secrets/credential.key` on first use.

Only administrators mutate instance settings. They separately gate personal providers and models, personal tool settings, and integration adapter availability. Each registered integration adapter is `full`, `instance_only`, or `disabled`; a missing setting defaults to `full`. Agent-executed adapters support only `full` and `disabled` because their instances are owner-bound. Effective AI settings retain instance providers and add enabled personal providers, with valid personal model defaults overriding instance defaults. Effective integrations retain instance instances unless their adapter is disabled and add personal instances only for fully available adapters; agent-bound instances must reference an `ExecutionAgent` owned by the current user. Availability changes leave configured instances stored, while blocked instances remain manageable but do not enter effective runtime use.

Tool settings expose separate private- and public-model defaults in the existing instance and personal scopes. Until a user saves one trust branch, the current instance values remain effective for that branch; saving stores the complete personal branch until reset. Disabling personal tool settings leaves both branches stored but makes the instance settings effective and blocks personal editing. Instance-controlled tool availability is a hard bound independent of policy values. The Webfetch user agent, response limit, and public-address restriction are also instance-only technical settings. Integration settings own technical connection configuration and trust-scoped integration and resource defaults plus CalDAV standard resources, even where the supporting persistence shares the tool settings document; the Tool gate and reset never suppress or remove those personal Integration values.

Infinity is host-controlled local infrastructure, not a selectable LLM provider. It is reachable only inside the Compose network and computes query, durable-memory, and prior-session message-chunk embeddings with a pinned multilingual model. pgvector stores this derived data in PostgreSQL beside canonical memories and messages. Backend availability does not depend on Infinity and falls back to PostgreSQL FTS. Ownership, current-session exclusion, source-session mode, and durable-memory audience filters are applied in SQL before vector limits; the local embedding service never grants visibility.

The authenticated global search reuses the same message-chunk FTS and embedding index instead of maintaining a separate UI index. Project names and session titles use owner-filtered substring matching; message results use hybrid lexical and cosine ranking and remain available as lexical results when Infinity is unavailable. Like model-facing prior-session retrieval, direct owner search spans all of that owner's projects and standalone sessions. Eligibility still differs: UI search may include the current session and sources in any memory mode. It may return both message trust levels because the authenticated session API already exposes that owner's canonical transcript. Every search lane applies the owner filter before ranking and limits.

## Memory Boundary

Normal project memory context has four layers: canonical current-session context, every visible pin in full, a compact project-session index, and bounded automatic snippets from relevant unpinned memories and prior sessions. The separate owner-scoped user profile is projected independently of `memoryMode` between assistant persona and project context. Its six maintained fields support shared and trust-specific values, are not embedded or searchable, and suppress exact normalized duplicates from every memory retrieval path. Current user statements override the profile, which overrides durable and prior-session memory. Every eligible turn builds one latest-message or short-follow-up query and shares one embedding across both automatic search lanes, with PostgreSQL FTS fallback. Fixed configurable quotas default to two memory snippets, three relevant-session snippets, and two recent snippets for bootstrap or explicit recent-session overviews. The fully serialized automatic payload defaults to 1,024 tokens and is capped at 10% of usable input. Pins are outside that budget; projection retries without automatic snippets but fails safely if the complete visible pins cannot fit.

Automatic relevant and recent source sessions must be `full`, must belong to the same owner regardless of project membership, including standalone sessions, and must not be the current session. Project requests receive up to ten recent eligible sessions from the same project ordered by their latest eligible message; the bounded index contains titles and exact `session_read` arguments but no message content. The project-session index and project sidebar remain project-local. Project requests then spend the remaining automatic budget on relevant snippets from distinct owned sessions before non-overlapping recent snippets and unpinned memories of any source provenance. A semantic session reference carries only the strongest topical anchor. Optional project instructions remain the authoritative place for deliberately maintained project rules; they complement rather than replace session evidence. Receiving `full` and `read_only` sessions may use the context; `disabled` sessions receive none. Authenticated UI search and explicit permission-controlled session tools continue to cover owned `read_only` and `disabled` sessions. Persisting eligible messages creates deterministic search chunks and FTS transactionally, embeddings remain asynchronous, and lexical retrieval remains available when embeddings fail.

Dreaming processes only `full` chat source sessions, never automation sessions, and extracts durable user-specific knowledge outside the maintained user profile, including lasting technical facts and long-term project involvement but not temporary equipment, current work, or implementation details. Candidate-local reconciliation supports exactly `create`, `unchanged`, `update`, `merge`, and explicit-evidence `remove`; uncertain identity defaults to `create`, an unmatched removal never creates a record, and age, non-mention, or weak relevance never justify deletion. Every new Dreaming memory is unpinned. Updates and merges preserve existing pins but never promote records.

Dreaming has only update and remove policies, defaulting to `auto` and `ask`. A merge requires both: either `disabled` skips it, either `ask` creates one approval, and only both `auto` apply directly. Persistent `memory_change` approvals store and revalidate exact target and policy snapshots under lock, and stale requests cause no partial mutation. Merge preserves evidence and pinning and deletes redundant rows in the survivor transaction. Durable memories, retrieval, approvals, and Dreaming runs are owner-scoped.

## Provider Boundary

Provider adapters transport model messages, tool schemas, tool choice, text deltas, and tool calls. They never execute tools or manage sessions and file permissions. Responses API function tools explicitly disable strict mode so provider-side schema normalization cannot turn optional host arguments into required model arguments; MatoLoop validates every returned call itself.

- `openai-codex` uses the ChatGPT device-code flow suitable for self-hosted interfaces and isolated Codex Responses and image-generation transports. Login requires neither a public callback URL nor a local callback port.
- `openai-compatible` supports Chat Completions and Responses API.
- `lemonade` uses Chat Completions and the native image, speech, audio, and transcription endpoints of a Lemonade server.
- Every adapter implements the same internal provider contract.
- The direct ChatGPT Codex endpoint is not a public OpenAI Platform API and remains encapsulated in its adapter.

Technical provider responses are logged server-side and mapped to safe domain errors such as `provider.authenticationFailed`, `provider.rateLimited`, or `provider.unavailable`.

Providers and models have a one-to-many relation in typed AI settings. OpenAI-compatible providers synchronize model IDs through `GET {base_url}/models`. ChatGPT Codex uses its OAuth credential with the private catalog at `GET https://chatgpt.com/backend-api/codex/models`; the adapter adds the native `openai-codex/gpt-image-2` media model with `image_generation` and `image_editing` and keeps the private Codex contracts encapsulated. Credentials never leave the backend. External OpenAI-compatible model IDs remain opaque strings; Codex slugs use the `openai-codex/` namespace. Newly discovered models start disabled except host-declared native media companions, while manually added models provide an explicit fallback.

Lemonade synchronizes installed models only and maps documented labels and recipes to the provider-neutral capabilities `chat`, `image_generation`, `speech_generation`, `audio_generation`, and `audio_transcription`. Image input, tool calling, and parallel tool calls remain separate chat runtime properties. Media resolution first uses an active model with the requested executable capability, then a native media model from the active provider, and finally the explicit global capability default. Image editing reuses the image-generation default only when that model also advertises `image_editing`; it has no separate default setting. Media-only models never appear in chat, compaction, title, or dreaming selectors. Omni collections are not offered because their server-side tool loop would bypass MatoLoop permissions and persistence. Unknown recipes are not inferred from model names. Lemonade image generation omits an unspecified size, step count, and CFG scale so server-side model defaults remain effective; the discovered `Z-Image-Turbo` model therefore keeps its catalog defaults instead of receiving a host-imposed `512x512` size. Every media tool has a host-controlled timeout, 300 seconds by default. Provider timeouts are reported separately from other availability failures as `provider.timeout`, including the timeout and retryability for agent and direct API callers; technical details remain in safe server logs.

Lemonade owns model residency and prompt-cache lifecycle. MatoLoop does not load, unload, or pin models because those operations reserve shared host RAM or VRAM and depend on the administrator's `max_loaded_models` policy. Administrators may preload a frequently used model through Lemonade and pin it against eviction; the number of simultaneously pinned LLMs must fit that policy. Residency avoids model cold starts, while llama.cpp prompt caching reuses common token prefixes only while the model remains loaded. MatoLoop requests streaming usage metadata from Lemonade and directly discovered llama.cpp models and persists any provider-reported cached input token count with the private assistant performance data.

Every LLM provider has a required `public` or `private` trust level. A model can override it in either direction or inherit it with `null`. Starting a run persists the model, effective trust, and pseudonymization snapshot. Selecting a model is the user's release decision for all content already authorized for that run, so changing to a public model does not add a second message, attachment, tool-result, file, or integration release approval. Ownership, project and root access, memory audiences, tool policies, grants, and approvals remain independent boundaries. Messages retain run trust as provenance; sessions have no aggregate trust level.

Local identifier and secret protection is enabled by default for effectively public models. Independent Presidio recognizers detect email addresses, IP addresses, phone numbers, IBANs, and credit-card numbers with checksums and specialized validators to limit false positives. `detect-secrets` adds structured API keys, tokens, secret assignments, and private keys. Free entities such as people, places, organizations, product names, and technical terms are not modified. Detected values become random request-scoped markers; text deltas, reasoning summaries, and tool arguments are restored before local persistence. A host instruction tells the provider to preserve markers exactly. Unknown markers from the current request abort processing before tool arguments can be used. Mapping and nonce exist only in memory for one request. Opaque continuation data is neither replayed nor persisted in this mode because it cannot be inspected locally. Images and binary data have no separate content pseudonymization. Detection is best effort and does not guarantee recognition of arbitrary confidential statements or source code. Disabling it deliberately sends released context unchanged to the public provider.

Discovery does not replace local configuration. Known models keep their internal UUID, enabled state, and runtime values. Missing discovered models are marked `missing` and removed from effective selection, not deleted. Manual and discovered model configurations can be deleted; deletion clears matching defaults in that settings scope and its explicit session selections, while a later synchronization recreates a still-advertised model with a new internal UUID. A failed synchronization leaves the last valid state unchanged. Effective model availability requires an active provider, an active model, current discovery availability, and an existing Codex connection where applicable.

AI settings define separate defaults for agent runs, context compaction, title generation, and vision helpers. Only available tool-capable chat models can be agent defaults or session models; compaction and title generation remain tool-free internal requests. Session selection overrides the agent default. Reasoning profiles advertise the supported effort variants and model default. Without a compaction default, compaction uses the session model and finally a deterministic summary. Without a title default, title generation uses the session model or agent default. Attachment-only titles use extracted text or filenames; images use an image-capable title model or, when the default-enabled vision fallback is active, the configured vision model. A failed model request leaves the locally derived title. Invalid default references are removed when the model catalog changes.

## Integration Boundary

Integrations are configured instances of a capability and a host-registered adapter. Every instance has a stable ID, enabled state, optional credential reference, and typed provider-specific configuration in either instance `IntegrationSettings` or owner-scoped `UserIntegrationSettings`. The adapter registry is also the integration catalog; availability is stored by adapter type, so newly registered adapters appear without a second catalog list and default to fully available. Instance integrations and their remote resources are intentionally shared with all users under instance tool policies. Personal instances and credentials are owner-only and enter the effective set only for fully available adapters. Configuration can activate only known adapters; external services provide no executable code, arbitrary custom tools, unchecked tool schemas, or prompt text.

Every adapter has a static `backend` or `agent` execution location. Backend adapters cannot be assigned to a MatoLoop Agent. Each agent adapter is bound to one configured `ExecutionAgent` and is offered only when that agent is the immutable executor snapshot for the run and advertises the host-known operation. Multiple MatoLoop Agents and one local integration instance per adapter kind and agent are supported; models never select an execution location per call. See [integrations.md](integrations.md).

OpenCode is a personal-only backend adapter. Its HTTP client, remote sessions, repository reads, models, event stream, and permission replies remain adapter details; the project service exposes only the generic coding binding, analysis, plan, and execution contract.

An adapter can contribute statically known tools, controlled prompt fragments, or values for explicitly declared host configuration fields. Before each model request, available tools form an immutable effective tool set. The same binding snapshot exports the schema, validates returned calls, and executes them; calls not offered are rejected. Host tool options do not become model arguments. Security-relevant configuration is reloaded immediately before an external effect. See [integrations.md](integrations.md).

The integration policy core is domain-neutral. Adapters declare host actions, stable shared tools, typed arguments, and optionally one resource level under an integration instance. A resource may narrow the adapter-declared capabilities that apply to it; remote data cannot add capabilities. Effective built-in defaults come from Tool settings; integration and resource defaults come from Integration settings. A selected `AgentProfile` adds sparse `private` and `public` capability, integration, and resource overrides, and the frozen run trust chooses the applicable override map. Missing entries live-inherit the effective defaults, so later default changes apply without rewriting profiles. A scoped profile override may replace a capability, integration, or resource policy, but no profile can restore a technically unavailable tool or resource, a disabled integration, or a capability removed by a remote ACL. `disabled` denies, `ask` uses the persistent approval loop, and `auto` skips only that approval. Grants bind the profile and trust level in addition to their exact resource matcher. CalDAV uses account and calendar or task-list defaults, while IMAP/SMTP mail uses account defaults only. Future repository or device integrations must reuse this core rather than add domain policy tables or runtime dispatch branches.

Profile-level integration selection is independent of these action policies and model trust. `integrationsEnabledByDefault` controls inheritance; sparse `integrationAvailability` entries use canonical integration UUIDs with strict `true`/`false` overrides, while an absent entry inherits. Switching the default preserves explicit entries and does not mutate integration enablement or existing private/public resource permission maps. The runtime filters before resolving contributed tools, shared accounts/resources, host options, or project coding capabilities. This includes OpenCode, OpenSCAD, and option-only SearXNG. An excluded primary search instance makes `web_search` unavailable instead of silently selecting `no_key`; an excluded fallback is removed. Explicit `no_key` search remains independent of integration selection.

Selection, binding revisions, and resource policy remain revocable before effects and after approval, including nested directory approvals and aggregate resource reads. An approval never revives an excluded integration or revoked resource. Delegation freezes concrete enabled integration UUIDs and the intersection of offered and spawn-time permission ceilings, then applies stricter live policy. Newly configured or newly enabled integrations cannot widen a running child. Resource filtering reuses the existing sparse maps and typed matchers rather than introducing another permission store. See [harness.md](harness.md#tool-contract).

## Browser Boundary

Internal chat navigation retains the original browser/view connection and model attachment independently of the displayed session. Other chats cannot operate that connection without takeover. The instance-bound `browser_request_control` tool is available before attachment and uses the existing permission system with `browser.control=ask` for both public and private models. Authorization opens the Browser app in the same displayed requesting chat and permits implicit takeover, followed by model attachment only after graphical readiness. It does not override read/write/code policy. The bounded, single-client request is revalidated against its live run and reviewed binding; cancellation or expiry cannot leave latent attachment authority. There is no automatic chat navigation or headless fallback.

Browser runtime architecture and operations are documented in [browser.md](browser.md). This optional personal agent integration combines a persistent per-agent Chromium profile with one live noVNC viewer and explicit chat attachment. Small `browser_*` tools share the Python Playwright worker and the existing execute transport; no official MCP runtime is embedded. AUTO calls resolve refs without whole-page hash preconditions. Actual approval waits retain bound state checks, and every required capability is revalidated afterward. `browser.read`, `browser.write`, and the distinct `browser.code` capability default to AUTO for both model trust levels; explicit restrictions remain effective. Both Python `browser_run_code` and page-JavaScript `browser_evaluate` require all three. Python deliberately has the browser worker account's OS rights, including accessible files, processes, network and profile data; those operations are not individually inspected by shell/filesystem tool policies. This accepted code authority is not a browser-only or whole-agent sandbox, and requires external isolation or disabled code permission where that scope is unacceptable. The existing renderer sandbox, owner-bound API checks, private desktop transport and ephemeral screenshot lifecycle remain separate guarantees.

## Channel Boundary

Channels are owner-bound message ingress and egress endpoints, not integration instances. They do not contribute agent tools, prompts, policies, or resources. Administrators control a separate global allowlist of host-installed channel providers; personal endpoint records and encrypted credentials remain stored but are not effective or shown while their provider is disabled. Administrators manage only this allowlist and cannot inspect another user's endpoints or credentials.

Every external event enters the normal persistent session, message, and agent-run flow through a deduplicated inbox. Messages retain immutable channel provenance, while sessions derive only a default reply channel and remain channel-neutral. External delivery uses a persistent outbox. Automation definitions may retain an owner-bound endpoint selection, but each run snapshots its effective destination; a provider disabled at enqueue time falls back to the canonical MatoLoop app result. Pending external deliveries are terminated when that provider is disabled and are never replayed after it is enabled again.

Channel providers may project the existing provider-neutral run-event stream as ephemeral typing, compact activity, or response previews. These projections are best-effort, process-local acceleration and never replace the canonical persisted assistant message or persistent outbox delivery. Runtime events carry the same host-controlled German activity labels used by the frontend and channel projections. Telegram uses native private-chat drafts for public reasoning summaries, tool activity, status, and streamed response text. Tool arguments, results, process output, and metadata remain outside the draft. Telegram sends the final response only through the normal outbox.

Outbox text retains its canonical `plain` or `markdown` content format. A small channel-renderer registry converts that source into provider-specific, independently valid text parts only at preview or delivery time; limits, markup syntax, safe degradation, and splitting remain provider-owned. Missing renderers and legacy payloads without a content format use plain text. Telegram renders the supported Markdown subset as escaped Telegram HTML and degrades unsupported or oversized structures without changing canonical message persistence.

Run-bound agent-action approvals originating at an endpoint add a typed provider-neutral action envelope to the same outbox transaction. Adapters render only its host-controlled summary and available decisions as native controls when supported; an adapter without controls may expose only the envelope's exact UUID-token command forms. A decision is accepted only from the paired owner and destination of the delivered prompt after revalidating endpoint, inbox, source message, session, run, approval status, and available action under lock. The shared approval service remains authoritative and treats an identical provider retry idempotently. Shared-shell approvals use this ordinary path too; an edited draft invalidates an older review and must be reviewed again in MatoLoop. Skill build or edit approval still requires exact draft-revision review in MatoLoop; channels can only deny that request.

Voice messages use the same provider-neutral attachment and runtime pipeline from the web composer and messaging channels. Channel adapters download and classify media, marking voice recordings with `voiceMessage` attachment metadata; they do not transcribe them. Web multipart requests identify recorded audio through validated `voiceAttachmentIndices`. Only the original recording is persisted before the runtime attempts automatic transcription with the owner's configured transcription model. Recognized text supplements the user message under the normal message-length limit; unavailable or failed transcription never removes the recording or inserts error text as user speech. Each attempt commits its terminal status with the transcript so run retries do not append it twice. A `message.updated` event accelerates delivery of the canonical message. Marked recordings request transcription directly, without a separate model-tool approval; model-initiated transcription retains its normal permission loop. Ordinary audio uploads are not automatically transcribed.

Voice recordings remain playable and accessible through the existing attachment tools regardless of ingress provider. All audio entry paths, including ordinary uploads and generated or downloaded artifacts, persist only the original audio, without a new WAV companion or companion metadata. Ingestion still validates audio through the bounded processing pipeline. Transcription and browser playback fallback convert the verified original to transient PCM WAV on demand through that same pipeline, off the event loop; downloads retain the original format. Existing audio companion metadata and managed files are ignored for audio reads and model context, but left intact because other attachments, file actions, or revision references may still use them. No cleanup migration is required for compatibility; reclaiming legacy storage requires a separate reference-safe cleanup mechanism, not the transaction rollback discard helper. Text and document companions remain persistent. Web recordings are previewable before sending and use the existing attachment limits and persistent message outbox; unsent recordings are not server-side session storage. Telegram polling, media download, progress, callback acknowledgement, and outbox delivery release database transactions before Telegram API I/O.

Agent questions use a provider-neutral, versioned outbox envelope. Telegram projects it as a
sequential inline keyboard and accepts custom or free-text values only as direct replies to the
delivered prompt. Navigation changes only the envelope state; submit and reject use the same
question decision service as the HTTP API. Each interaction locks and revalidates the endpoint,
owner, originating input, session, active run, delivered outbox prompt, and pending request.

## Agent and Tools

Static host-controlled prompts, repair instructions, prompt fragments, tool descriptions, schema descriptions, and model-facing markers use simple English. Contracts remain concise, explicit, provider-neutral, and free of redundant or contradictory instructions so medium-sized local instruction models and cloud models use the same text. Dynamic user, identity, memory, source, and tool data may use any language; exact German UI labels can appear as quoted product identifiers.

The shared tool prompt requires one compact standalone search query for exactly one information need. It prefers discriminative terms over sentences or task descriptions while retaining essential relationships and exact identifiers. Queries must not combine separate questions, synonym lists, or alternative formulations. If the model chooses a tool, it emits the call in the same response and does not announce future tool use without that call. Current searches normally omit a year; when a freshness year is required, it comes from the frozen local run timestamp rather than prior knowledge. Explicit user years and years in exact names, versions, historical scopes, and comparisons remain unchanged. The `web_search` schema describes only the form and purpose of its sole `query` argument. MatoLoop never rewrites search queries.

Plan and Build are task-general workflows, not repository-only roles. Main Plan analyzes relevant evidence without carrying out the requested changes and retains the canonical managed artifact `plans/<session-id>/plan.md`. Build performs the requested work, verifies appropriately, and may answer inline when that fulfills the request. Applicable `AGENTS.md` instructions are read before repository edits, not required for unrelated tasks, and cannot override host rules or the latest user request. Generic writing is not forced into a file unless a saved artifact is requested or a workflow requires one. Saved artifacts retain one file and reuse its path for revisions. Delegated prompts supply self-contained goals and evidence without imposing the main workflow on children.

The backend agent runner owns the provider-neutral model and tool loop. No-key metasearch and SearXNG remain backend operations; computer operations are dispatched to the run-bound MatoLoop Agent. Providers never execute tools.

## MatoLoop Agent Boundary

The backend remains authoritative for provider communication, the LLM and tool loop, static schemas, argument validation, model policies, approvals, grants, sessions, memory, credentials, backend integrations, session storage, and canonical tool results. A standalone MatoLoop Agent belongs to exactly one user and connects outbound over the authenticated strict protocol v1. Its required hello fields are `agentId`, `agentVersion`, `computerName`, `platform`, `homeDirectory`, and `operations`. `homeDirectory` is a normalized absolute POSIX path. The agent advertises no roots, root IDs, or root revisions, and there is no compatibility protocol. It receives bounded authorized operations, not the system prompt, chat history, provider credentials, or permission authority.

The hello also carries an optional, strictly validated `systemInfo` snapshot: operating system, distribution/version, kernel, CPU model, architecture, logical CPU count, and total RAM in bytes. Agents refresh it on every connection; omitted or null measurements are unknown. The backend retains it only on the live connection, replacing it on reconnect and removing it on disconnect or revocation. The shared model context includes these descriptive data only for the run-selected, owner-bound, non-revoked connected agent, including delegated runs, never from another computer or the backend. This static connection metadata requires no tool approval and grants no permissions; live `get_system_info` queries retain their existing permission checks. Reported system totals are not container resource limits. There is no persistent hardware inventory or periodic telemetry. Older agents may omit the snapshot; deploy the backend update before newer agents because older strict backends reject the new hello field.

MatoLoop Agents pair through a bounded one-time registration token. The agent generates its durable access key locally and submits only its SHA-256 hash; after pairing, only that durable key can authenticate WebSocket and transfer requests. Unpairing commits the credential removal before closing the live connection and revoking unclaimed transfer tickets.

The backend retains the stable implementation identifiers `ExecutionAgent`, table `execution_agents`, API `/execution-agents`, and foreign key `execution_agent_id`. They name the persisted domain aggregate and are not standalone product or deployment names.

A new session has only owner-bound internal session storage and no workspace. After the user selects an owned, non-revoked MatoLoop Agent and directory, the session persists that normalized absolute current directory. The required agent home is the default starting point for directory selection, not an advertised root or backend workspace. Starting a run resolves and snapshots the selected agent, current directory, and advertised operations. Changing directory updates the run and session together so the next model request observes it; retries start from the session's current directory. Disconnects do not switch to another agent or the backend, and dispatched operations are not automatically retried or redelivered. An offline selected computer does not block normal chat or backend tools, but the run has no live computer operations.

Model-initiated computer directory grants use canonical JSON `{agentId,path}`. Matching compares normalized absolute POSIX path components, never string prefixes. A requested directory is resolved through the MatoLoop Agent first, then requires the applicable per-computer filesystem policy and, for `ask`, an existing covering grant or an `allow_session`/`deny` approval. Directory grants are independent from operation-specific file and process policies.

File roots retain one model-facing contract; internal persistence and permission code may translate these names to `session` and `workspace`:

```text
root=files    -> backend-managed revisioned files
root=computer -> selected owner-bound MatoLoop Agent directory
```

The backend mediates cross-root and user-facing file transfers with short-lived, owner-bound HTTP tickets. Both sides enforce size limits and validate byte count and SHA-256 before accepting content. The MatoLoop Agent's sparse session cache contains only files used by authorized operations, is size-bounded with oldest-file eviction, and validates size and SHA-256 on every hit. It is never canonical and may be cleared without losing session data.

Each `ExecutionAgent` record has `auto`, `ask`, or `deny` filesystem policies for the home and external zones, defaulting to `auto` and `ask`. It also has hard boolean shell switches for those zones, both enabled by default. Filesystem policy classifies normalized absolute paths against `homeDirectory`. Before `shell.run`, `shell.inspect` resolves the current directory and direct targets; every applicable shell zone must be enabled, and incomplete analysis requires the external zone to be enabled.

Every standalone filesystem operation is named `filesystem.*` and uses normalized absolute POSIX paths. The MatoLoop Agent operates with its operating-system user's rights and traverses from an open `/` descriptor with no-follow checks on every path component. These checks prevent symlink traversal but do not create a sandbox. The Docker image currently runs as root and has only `/data` and `/workspace` mounted, so mounted scope and deployment policy are the effective filesystem boundary. Native agents retain the rights of the user that starts them.

Direct authenticated Control Center filesystem requests are owner-bound but intentionally bypass model permission policies and grants. They may access anything available to the selected MatoLoop Agent's operating-system user, subject to protocol validation and descriptor/no-follow checks. This direct browser path is not available to the model.

The built-in Control Center Terminal uses an authenticated, same-origin or explicitly allowed-origin browser WebSocket through the backend to the selected owner-bound MatoLoop Agent. It opens one managed Bash 5 / Readline 8 emacs-mode shell on Linux, starting in the agent home directory. Personal commands run directly with the agent operating-system user's rights, outside model policies and grants. **Agent verbinden** routes the session's `shell_run` calls into that same actual PTY, sharing cwd, environment, variables, aliases, functions, and history rather than replacing or hiding the personal shell. Personal use remains available between agent commands while attached; staging waits for an empty primary prompt and does not overwrite personal input. Without attachment, `shell_run` remains isolated in the session's selected directory. The terminal's real cwd is independent of the chat workspace and file tools; neither attachment nor terminal `cd` synchronizes them.

There is no terminal Auto/Confirm selector or separate proposal overlay. Attached calls use ordinary shell inspection, effective policies, token-prefix allowlists, and session grants. An allowed call executes without a mandatory confirmation; a call needing approval creates the same persistent `shell_run` request in chat and **Benachrichtigungen**, with a read-only command/cwd review and the usual available decisions. Hard denials remain denials. The user can instead edit the real native command line: Enter freezes and reinspects that exact draft and resolves the same approval as `allow_once`, never bypassing hard policy checks. Draft, context, and inspection revisions bind acceptance to the reviewed text and physical cwd; stale reviews cannot authorize edited text. Ctrl+C while pending discards the draft and expires that approval, returning a denied tool result without cancelling the parent run. While running, Ctrl+C interrupts the foreground process group; the stop control in chat cancels the entire run.

The backend owns one live terminal runtime per owner, chat session, and selected agent. Browser disconnect, reload, session switching, and collapsing the Control Center leave the shell and attachment live without an idle timer; releasing a viewer does not close the PTY. The newest authorized viewer takes control and the replaced viewer does not automatically reconnect. Removing the terminal tab, losing the login/session/agent binding, shell exit, backend restart, or agent disconnect/restart ends that lifetime; reconnection may start a new shell but does not restore lost shell state. Backend replay retains a bounded raw-output tail (256 KiB), not a durable transcript or exact full-screen snapshot. Reconnection replays that tail without clearing the screen or forcing a prompt redraw. The UI reports truncation; slow viewers disconnect for resynchronization rather than blocking shell progress. Canonical tool results and approval records remain separately persistent.

Shared execution requires the agent's native Bash loadable module and compatible Bash/Readline ABI; missing support makes the shared terminal unavailable rather than substituting an isolated shell. While an agent draft is pending, a filtered native Readline keymap allows editing, history navigation/search, quoted insertion, and bracketed paste, but disables completion, shell expansion, external editors, bind-x callbacks, keyboard macros, and other non-editing functions. Checking freezes edits until acceptance or cancellation; personal bindings are restored afterward, and history expansion is disabled at managed prompts. These restrictions prevent pending source from executing before authorization, not arbitrary shell side effects. Context revisions do not fingerprint mutable variables, aliases, functions, or callbacks. This is approval coordination under the ordinary shell heuristic, not a sandbox. Native protocol and build details are maintained in [SHARED_TERMINAL.md](../apps/matoloop-agent/SHARED_TERMINAL.md).

Isolated execution and the shared Bash terminal use the same shell inspector. Every model `shell_run` command is parsed with the Bash tree-sitter grammar before execution and model-policy authorization. A recognized mutation makes the entire pipeline or command list `shell.write`; otherwise it is `shell.read`, even when analysis is incomplete. Shared execution adds no forced-write classification or special prefix/grant rules. Known mutations include non-exempt output redirection, filesystem mutations, mutating Git or package-manager operations, HTTP uploads or mutating methods, and nested mutating commands. The protocol field `readOnly` is a legacy alias for the read classification, not a guarantee of side-effect-free execution. Syntax errors return controlled `process.invalidSyntax`, not an approvable write classification. POSIX `<>` read/write redirection is supported and remains a non-exempt write, including `<> /dev/null`.

`docker exec`, `docker container exec`, and `docker compose exec` classify the inner argv with the same mutation rules after parsing known options and the container or service operand. Only explicit supported `sh`/`bash`/`dash` `-c` forms parse an argument as shell source; ordinary string arguments remain data. Nested Docker and shell calls are bounded to eight analysis levels. Ambiguous exec options, privileged execution, dynamic outer arguments, unsupported shell forms, and exhausted nesting retain the former write classification. Unknown inner programs follow the ordinary no-recognized-mutation rule, not a verified read-only guarantee. Container paths are not resolved on the agent host, so exec inspection remains incomplete and retains external-zone policy checks. Host-side Docker/Compose arguments, exec `--env-file` inputs, outer substitutions, and outer redirects retain host path checks; container redirects cannot use the host's verified `/dev/null` exemption. Exec units deliberately have no reusable permission prefix: existing broad Docker grants and prefix allowlists do not authorize them, and an approval offers only `allow_once` or `deny`. Effective `auto` policies still apply to the inspected class. Execution and revision checks remain bound to the original full command.

Command-text, directory-enumeration, and target-count technical bounds return `process.inspectionLimitExceeded` rather than authorize a truncated inspection. Serialized command-node and token caps instead mark extraction incomplete and remove reusable prefixes; inspection still visits later commands for known writes and hard path checks. A missing literal target retains its normalized absolute path and marks analysis incomplete when existence was required. Missing targets are distinct from hard no-follow or access failures, which still reject execution. The inspection result, target metadata, semantic token prefixes, and classification share one revision and are rechecked immediately before execution; changed inspection returns `process.inspectionChanged`.

Two shell-only target kinds skip only the soft outside-current-directory path approval. A static output redirection to exactly `/dev/null` is non-mutating only after no-follow verification of the real character device with major/minor `1:3`; its `discard` target remains in the inspection revision and hard zone checks. Dynamic destinations, other devices, input use, and POSIX `<>` receive no discard exemption. `toolchain_metadata` covers only simple installed `ls` discovery in the actual fixed execution `PATH`: `/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin`. Supported operands are flat directory listings or direct basenames and basename globs, with only the restricted `--` and `-aAldh1` option forms. A bounded listing fingerprint binds the observed entries to the inspection revision. Recursive or dereferencing options, wrappers, and arbitrary directory symlinks receive no exception. Only verified standard `/bin` and `/sbin` usr-merge aliases are handled specially; basename file links require a verified one-hop regular-file destination, and hidden or out-of-directory destinations retain ordinary path checks. Dot globs that can include `.` or `..` retain ordinary directory targets, including `/usr`; `/usr` itself is not exempt. Large basename matches may fall back to an ordinary directory target, never silently drop hard paths. If the same path also appears as ordinary content, the ordinary path policy wins. These helpers are inspection-only: direct file read, write, edit, patch, and delete behavior is unchanged.

Effective tool settings default `shell.read` to `auto` for private models and `ask` for public models; `shell.write` defaults to `ask` for both. Class-specific token-prefix allowlists may satisfy `ask`, but never override a disabled capability, ownership, a hard shell-zone switch, filesystem `deny`, confidential-path restrictions, or current revision checks. Session grants cover the inspected prefixes only for the same class, agent, absolute current directory, profile, and trust level and remain revocable. The optimistic `shell.read` classification is an accepted, intentional workflow tradeoff. It is a permission class, not a guarantee of side-effect-free execution. Unknown programs, tests, and builds may be classified as read operations to keep coding workflows usable. Complete effect analysis and an OS sandbox are not prerequisites for the native coding agent. Reviews should report concrete regressions in classification, approvals, revision checks, or enforced boundaries, rather than repeatedly treating this documented residual risk as an unresolved defect. Revisit this decision when new evidence or a changed deployment threat model warrants it; deployments may independently choose stronger isolation.

Process startup binds the working directory to an opened descriptor, using procfs for ordinary subprocess startup and `fchdir` for PTYs. One-shot commands receive the canonical current-directory path as logical `PWD` and `HOME`, never a procfs descriptor path; the detached user terminal starts in the agent home. Validated canonical executable paths preserve shebang script paths and `$0`. This is path-based execution: validation is not atomic with exec and does not pin executable identity through a descriptor. The working-directory protection must not be described as secure descriptor-based execution or an OS sandbox.

## Working Directories and Approvals

Standalone managed roots are `/data/sessions/<session-id>/{files,revisions}`; project managed roots are `/data/projects/<project-id>/{files,revisions}`. Attachments are managed files in these roots, with no separate attachment storage. Moving a standalone session into a project imports all managed files and complete revision histories and rebinds their references to the project root. Moving a project session to standalone creates a new empty session root while its former project files remain in the project; moving it from project A to project B selects B while its existing files remain in A. File and attachment references are available only while their root is active. The model-facing `computer` root is the current absolute directory on the selected owner-bound MatoLoop Agent.

Tools have one of three execution types: `backend`, `computer`, or `shared`. Backend Tools execute inside MatoLoop, Computer Tools execute through the selected MatoLoop Agent, and Shared Tools keep one model-facing contract while selecting the backend session store or computer directory from their arguments. `tool_type` is host metadata and is never a model argument.

The Shared Tools `read`, `glob`, `grep`, `provide_file`, `write_file`, `edit_file`, `create_directory`, `delete_path`, `copy_path`, and `move_path` are filtered by storage availability and effective policies, not by an agent mode. Backend managed-file mutations use `session.files.write`. MatoLoop Agent access first applies the home or external filesystem policy for the normalized absolute target; operation-specific write and delete capabilities remain separate. No approval can supply a missing current directory or unavailable MatoLoop Agent operation.

`read` reads either a directory or UTF-8 text file with one-based `offset`, bounded `limit`, and numbered file lines. Large files are read in chunks, individual long lines are bounded, and tool output indicates continuation. `glob` searches file paths and `grep` searches file contents with fixed result, output, and time limits. Both searches use ripgrep without shell execution, configuration files, or symlink traversal. Copy and move validate source and destination roots before effects; the destination path always names the exact new entry and never overwrites.

Configurable permissions use persistent approval requests. The agent run waits for `allow_once`, `allow_session`, or `deny`; the request remains an inline chat card until decided. The UI defaults to `allow_once` and sends `allow_session` only when the user explicitly selects the revocable session option. Requests that cannot safely create a session grant expose only their narrower decisions.

Permissions use resource-specific matchers. File scopes contain root type, host-bound root identity, and relative POSIX path; legacy global path scopes are rejected. URL access compares exact hashes of complete canonical URLs, session access compares UUIDs, and session discovery uses a separate collection scope. `session_read` can read the current session without approval; another session requires an exact `session.read` grant or approval. `session_tool_result_read` reads only a known tool message in the current session without approval. `session_browse` and `session_search` share the `session.search` capability and collection grant and cover owned sessions across all projects and standalone sessions, excluding the current session. Discovery releases only a bounded preview; canonical transcript windows still require `session_read`.

## Context and Compaction

Agent identity uses an instance-scoped `AgentIdentitySettings` document and an owner-scoped `UserAgentIdentitySettings` document, separate from memory and tool policies. Display names remain independent from reusable persona profiles. Administrators separately gate personal names and personal personas; disabled personal values remain stored but ineffective. Instance agents can select only instance personas, while personal agents can select effective instance or personal personas. Every normal run resolves exactly one persona from the agent reference, applicable personal default, instance default, and built-in fallback, in that order, then projects it below immutable host rules separately from the agent's task instructions. A project session also receives its project name and instructions once per run. Immutable host rules and the latest explicit user request retain precedence. Deleting a custom agent profile atomically switches referencing sessions to the built-in default and removes their profile-bound permission grants; historical runs retain their profile provenance. The host-controlled `update_agent_identity` tool follows global `disabled`, `ask`, or `auto` policy and can mutate only permitted personal identity values; see [agent-identity.md](agent-identity.md).

The maintained user profile is a separate user-scoped `UserProfileSettings` document. The `update_user_profile` tool follows its own `settings.user_profile.update` policy, defaults to `ask`, and accepts only the six maintained fields plus a private, public, current-model, or both-model scope. The prompt contract permits calls only for explicit persistent changes in the latest user message and treats quoted, retrieved, remembered, web, and tool data as non-authoritative. The handler resolves current-model scope from the selected model trust level, acquires the user settings lock, and applies only supplied fields. Explicit null clears a field in the selected scope. Profile and persona settings deliberately have no optimistic revision contract; serialized writes use last-completed-write semantics and affect model context from the next run.

Complete message history remains canonical in the database. Before each model request, the context manager creates a transient projection from the stable host prompt with persona, user profile, and project context; an optional summary and older original history; a host-marked assistant context containing current-turn memory metadata and untrusted memory references; and the latest user request followed by any current tool round. The stable system prompt defines the assistant marker's trust boundary. This preserves a reusable provider-cache prefix while keeping the complete memory context in the same input budget. Automatic snippets can be dropped to fit; pins remain outside their budget, and projection fails safely if required context and all visible pins cannot fit. Full unpinned memory detail requires `memory_retrieve`, and full prior-session detail requires `session_read`. Selecting the model is the release decision for already authorized messages, tool results, and attachments, so public model trust alone does not redact them. Ownership and session permissions still govern access, and durable memories retain their independent `private_only`, `public_only`, or `both` audiences. Local pseudonymization remains separate. Tool calls and results remain paired, interrupted calls receive terminal errors, and tools are never re-executed during projection. Older large tool results become retrievable references, while current results share the available context budget and shortened search or webfetch envelopes remain valid. Canonical content and provenance remain unchanged.

Context window, Auto or manual output ceiling, characters-per-token estimate, and tool, parallel, streaming, and image capabilities are configurable per model. Context configuration accepts at least two tokens, but runtime safety and generation reserves still have to fit. Discovered models store the latest provider context value separately from the effective window. New discovered models follow that context value automatically; a manual context override stops automatic context updates and can later return to the provider value. If no provider context value exists, the fallback is 128,000 tokens. Existing persisted context overrides remain unchanged.

Adapters normalize context metadata for the selected endpoint, not a model-name catalog. Codex exports both its default `context_window` and allowed `max_context_window`; automatic discovery prefers the allowed maximum and falls back to the default when absent. Lemonade's configured server context still takes precedence over its model maximum. These are per-model values, not a global context ceiling. Existing provider-following models receive updated values on the next explicit provider synchronization; no live settings are rewritten by deploying the adapter change.

`maxOutputTokens: null` means Auto and is the default for new models; a strict positive integer is a manual ceiling. It is not clamped to a quarter of context capacity or rewritten on context changes. `discoveredMaxOutputTokens` is read-only and nullable: only OpenRouter's documented `top_provider.max_completion_tokens` currently supplies an authoritative output cap. Unknown output caps remain unknown, rather than being inferred from generation defaults, model names, or context size. Synchronization refreshes this cap for matching manual models as well as discovered models without replacing their manual output ceilings.

Data-only migration `49e718887770` switches all existing models in every instance and user `ai` settings document to Auto once, including explicitly configured manual output limits and legacy nested fields. It has no relational schema change and preserves context, reasoning, temperature, and other configuration. This is a destructive reset of old output ceilings without a backup. Downgrade removes output settings, including subsequently entered manual ceilings, to use older compatibility defaults; it cannot restore historical values. Normal use after upgrade preserves newly entered manual ceilings.

Current tool output has no fixed token cap. After any required compaction, the context manager subtracts system prompt, tool schemas, summary, conversation, images, and historical tool references from the model-dependent compaction threshold and shares the remainder among current tool outputs. Markdown and text are shortened near block boundaries while search and webfetch envelopes remain valid. Session-read and shell-result envelopes retain metadata and shorten text in the middle with explicit truncation markers. Session message IDs and pagination cursors are unchanged; shell exit codes, timeout state, and upstream truncation flags are preserved. If metadata alone cannot fit, the entire result is explicitly marked as omitted instead of emitting broken JSON or a partial page. Canonical results are unchanged. Historical tool output keeps a separate compact reference budget.

Ordinary input projection reserves `R = min(2048, manual ceiling M, known provider ceiling H)`, ignoring absent ceilings, plus fixed safety `S`. For context capacity `C`, the raw estimate budget is `raw_input_budget(max(0, C - S - R))`, where `raw_input_budget(capacity) = capacity * 10 // 11`. The compaction trigger uses the same inverse 10% margin after subtracting reserves from its ratio-based capacity. This reserves a useful generation turn, not the entire manual or adaptive output allowance. Every request projection is checked against the effective window of the model frozen for the run. Switching to a smaller model therefore triggers compaction before the next agent request when needed. Compaction writes a persisted `context_summaries` generation over a contiguous completed prefix and may advance within a long user turn. It keeps the latest user request and at least the last two complete current-turn tool batches in the projection and never covers a pending or partially completed batch. A covered current user message is restored only as a projection anchor, not repeatedly added back to the summary source after reload.

ContextManager receives an async raw-estimate callback backed by the same local `ProviderService.prepare_request` path used for completion. Every whole-request fit decision includes media selection, pseudonymization, tool-schema conversion, scope-matching continuation, and protocol serialization. Run attachment filtering precedes reference deduplication and estimation. To distinguish oversized history from large protected tool results, the manager estimates a copied projection with only tool bodies after the compaction boundary shortened as far as the existing shortener allows and compacts only when that request still exceeds the trigger. A separate minimum with all current tool bodies shortened determines their final shared budget. Both estimates retain unavoidable markers, short results, and privacy overhead instead of subtracting untransformed tool sizes from transformed request estimates. Character-based tool sizing remains a shortening heuristic, followed by shared request re-estimation. Preparation uses fresh original candidates without loading settings or credentials, refreshing tokens, or calling the transport. It repeats local image/privacy processing without a cache, while final completion retains its own request-scoped privacy restorer.

After the shared preparation, ProviderService takes `I = max(raw projection estimate, raw final serialized estimate)`, adds the proportional margin once as `guardedI = ceil(1.1 * I)`, and computes `min(C - S - guardedI, M, H, explicit helper ceiling Q)`, ignoring absent caps. For unchanged inputs the two estimates agree. Final revalidation remains necessary for changes such as attachment availability between passes; nonpositive output or failure to fit the required generation reserve produces a controlled context error before credentials or transport. There is no recursive compaction at the provider boundary. Input media estimates reserve 2,048 tokens per image and 8,192 per audio/video item or unknown opaque continuation, not a hidden media output cap. For scope-matching Responses reasoning replay, valid source-response reasoning usage plus a 256-token opaque framing allowance replaces the fixed reserve, divided across that response's opaque items with upward rounding. Missing, malformed, negative, or output-inconsistent usage retains the fixed fallback. This accounting stays local; no reasoning is removed or accounting fields transmitted. These character/media/usage heuristics are not actual-token guarantees; large inputs may require a manual output ceiling or still receive a provider error.

Host output-budget diagnostics remain separate from provider usage. Normal assistant `_matoloop.performance` records the final estimates, reserves, caps, mode, and both `allocatedOutputTokens` and `transmittedMaxOutputTokens`. The former is the computed allowance, not necessarily a transmitted or enforced limit. Codex omits generation options and records a transmitted value of `None` (`null` in JSON); compatible transports send their output-limit option. Adaptive allocation has no Qwen-specific rule and changes no existing reasoning or thinking behavior for any model. See [Model Context Settings](harness.md#model-context-settings) for the full allocation, helper, transport, and migration contract; this is not a live-provider validation report.

Summary input combines chat text with bounded allowlisted operational metadata and exact tool-result retrieval references, not arbitrary stdout/stderr or complete tool-result bodies. Already-authorized chat excerpts from `session_read` also enter the same request with a separate bounded allowance, deduplicated source IDs, and explicit attribution; nested tool bodies and references are never expanded. It retains relevant status, exit codes, counts, numeric results, paths, revisions, and failures as untrusted evidence with exact message/tool/call identifiers. A deterministic bounded evidence block is appended to each persisted summary, including coverage and earlier-history retrieval anchors. This preserves operational facts without treating successful execution as proof of task completion or promoting tool output to instructions. Full canonical results remain behind `session_tool_result_read`; projection and compaction do not re-execute tools or delete their output. See [Compaction](harness.md#compaction) for the bounds.

Compaction retains its bounded 256-to-2,048-token summary target under the helper model's manual and known provider caps, reserves the effective target in full, and uses the shared prepared-request allocation instead of a separate message-size preflight. Optional model reasoning is disabled when the existing reasoning profile supports it, and only a visible response with the required summary sections is accepted. An existing summary can be compacted again at the same boundary. The configured compaction model falls back to the active model and finally a marked deterministic summary. A single monotonic 20-second deadline (or the configured request timeout if shorter) covers all model attempts, transport retries, and backoff. Compaction uses a separate short-lived database session so cancelled credential operations cannot invalidate the run's transaction. Expiry cancels provider work and selects the existing deterministic fallback after session cleanup; external run cancellation still propagates. The transcript exposes every persisted generation and marks deterministic fallbacks with a warning. Projection and compaction never edit or delete original messages; only explicit undo or retry removes its defined suffix.

After the first message is persisted, the agent run and a separate tool-free title request start concurrently. The agent task is scheduled first; title generation uses only the first user message and never blocks the run. The title inherits that first user message's trust level dynamically; manual renames retain the same classification. `chat_sessions.title_generation_status` persists `pending`, `running`, `completed`, `failed`, or `skipped`. Only `running` with an unchanged local initial title permits final update. Manual rename sets `skipped` and wins races. Successful titles publish `session.title.updated`; status-based frontend polling remains a reconnect fallback. The first output line is limited to 80 characters. Title requests keep an explicit initial ceiling of 2,048 tokens rather than all Auto headroom. Empty or reasoning-only output receives one repair attempt up to 4,096 tokens; manual and known provider ceilings still apply. Reasoning is never used as title. Provider failures, invalid second output, cancellation, and orphaned `running` states found at startup end as `failed`; the local title remains. Existing sessions were migrated as `skipped`.

## Error Contract

API, SSE, tool, and persistent chat errors use one descriptor with stable code, controlled English fallback, and optional structured data:

```json
{
  "error": {
    "code": "validation.tooShort",
    "message": "The value is too short.",
    "field": "password",
    "params": {
      "minLength": 10
    }
  }
}
```

Required fields and channels:

- `error.code`: stable code for program flow and localization
- `error.message`: controlled English fallback for channels without localization
- `error.field`: optional affected input field
- `error.params`: optional values for dynamic text
- HTTP status: general failure class and fallback

English fallback text comes only from the central backend catalog. Pydantic details, exception text, and external provider responses never reach clients. Unknown syntactically valid codes remain intact with the safe `The action failed.` message.

The frontend localizes codes centrally in `apps/frontend/src/utils/api-errors.js` and always prefers the German translation over `error.message`. An Axios interceptor displays API failures as negative Quasar toasts. Persistent agent failures appear as MatoLoop chat responses and do not create a duplicate domain toast. Unknown codes use a safe frontend fallback based on HTTP status. Other channels may use `error.message` directly or localize `error.code` and `error.params` themselves.

## Notifications

Persistent in-app notifications are owner-scoped records with a host-controlled kind, plain-text display snapshot, producer-supplied deduplication key, and monotonic read timestamp. Producers create them in the same transaction as their canonical source state; the notification service never commits. Typed targets may reference a normal session or an automation run. A deleted optional session target becomes null; automation-run notifications are deleted with their owning automation history. Arbitrary URLs, generic source payloads, delivery state, retention, and external channels are not part of this record.

The Control Center exposes one global notification center, with required actions above durable informational notices in one scroll area. Its selected view is transient user-interface state and does not modify any session. Pending approvals and questions are read from their existing canonical tables, can be answered centrally, and disappear when resolved; contextual controls remain available in chat. Marking informational notices read individually or in bulk never dismisses required actions. The center badge sums pending approvals, questions, and unread notices. Legacy approval links open this unified view. Normal interactive chat responses and errors are not copied into notifications. Automation completions, failures, and exhausted output deliveries are persistent producers.

The Control Center keeps session settings, notifications, and a separated close button outside the horizontally scrollable app tabs, with 48-pixel touch targets. Tabs have no scroll arrows; a faded edge indicates overflow. Desktop additionally offers an open-tab menu when the strip overflows. Touch scrolling and keyboard navigation remain available, and selecting a tab brings it into view.

## Automations

Automations are owner-scoped definitions with one hidden, durable execution session and zero to fifty schedules. An explicitly empty schedule list creates a manual-only automation; the field remains required in API and agent replacement requests so omission cannot remove schedules. A schedule is either a five-field cron expression evaluated in an IANA timezone or one absolute execution time. One-time schedules reuse the materialized `next_run_at` value and have no cron expression or timezone. A cron schedule may have an inclusive `valid_until` instant; the schedule is exhausted when its next occurrence would be later. Enqueue stores the definition revision, task, optional skill, runtime configuration, output target, and triggering schedule snapshots. A process-local scheduler uses database row claims, skips missed downtime occurrences, and delegates every execution to the normal `AgentRuntime`; it does not resume or retry an interrupted agent stack.

Automation settings use a compact list and one canonical page at `/settings/automations/:automationId`, with settings and history tabs. The old `/edit` path and query-based automation links redirect to this page; `?run=` selects a historical run without replacing the local configuration draft. The editor groups task, execution, and result settings and discloses advanced options locally. Schedule presets map to the existing cron contract; unsupported expressions and unedited absolute timestamps round-trip unchanged. A bound skill is optional and enforces instruction loading, not tool availability. Status polling never replaces the editing revision or unsaved inputs; an observed revision conflict requires an explicit reload. Manual starts use only the saved definition and are disabled while the form is dirty.

The UI uses opt-in `summary=true` list and run-history projections, `/automations/:id/status`, and `includeHistory=false` when reading a definition. These typed compact projections omit execution transcripts, run results, and snapshots; active statuses are fetched in one batch for the list. Existing full API projections remain available for shipped clients. Only an opened run loads its full result and configuration; unchanged completed results are not repeatedly fetched. Polling is suspended when the document or relevant view is hidden, but visible summary polling continues to discover newly scheduled work. Paused definitions have no effective next scheduled start in compact projections. The internal execution transcript remains persistent and available through the existing full detail API, not duplicated in the ordinary UI.

Only one active run is allowed per automation. Schedules due at the same instant are bundled into one run; a due occurrence while another run remains active produces one persisted skipped run. Every consumed schedule follows one advancement path: a cron schedule receives its next allowed occurrence, while a one-time or expired cron schedule is disabled. Recovery uses the same advancement and skips missed occurrences. Manual starts may run disabled definitions. A definition with exactly one one-time schedule may opt into archival after its successful scheduled run; archived definitions retain history but cannot be scheduled, started, or edited. Terminal agent state is mirrored into the automation run. Completion and failure notifications are committed with that state. A completed run may deliver only its final assistant text to a normal chat as a host-marked assistant message; the session API exposes only its controlled source type so the transcript starts a separate assistant turn. Tool and reasoning records remain in the hidden execution session. Delivery waits for an idle target and has three technical attempts, independent of the immutable completed run state.

Built-in automation tools use owner-scoped service operations and session-bound permission scopes. Exact scopes include the automation revision so edits invalidate prior grants. Tool creation and edits can select only the invoking chat as a new output target; deletion cancels active agent runs before taking row locks and uses the same transactional storage trash/restore operation as the API.

## Frontend Interaction

Quasar components form the primary UI layer. Pinia stores hold server state; components coordinate presentation and user action.

Provider, **Standardmodelle**, integration, tool, and agent-profile pages expose **Persönlich** and **Instanz** scope to administrators. The tool page contains built-in tools only, supports the personal gate and reset, and keeps integration-provided tools absent. Integration configuration and its **Zugriff** page own technical settings plus integration and resource defaults, including CalDAV standard resources. Agent creation and editing share one routed page and store persona, instructions, and sparse private and public overrides that inherit those effective defaults. The personal side is always the signed-in administrator's own data, not another user's data. Non-administrators operate only on their personal scope, subject to the instance gates; shared instance resources remain available through effective runtime state without exposing stored secrets.

Permission requests persist optional structured display items alongside their authorization snapshot. The backend supplies resolved domain values that cannot be reconstructed safely from sanitized tool arguments, while the frontend uses one presentation path for approval cards and ordinary tool history. Approval cards may select a compiled tool-specific presentation from a static frontend registry; missing or incomplete registrations fall back to the generic structured presentation. Raw arguments remain available only as secondary technical details.

Destructive actions use `useConfirm` or `v-confirm`. More complex input and approval decisions use Quasar dialogs. Success messages appear at the initiating UI point; API failures are notified centrally only.

Unsent chat text is a browser-local draft and never reaches the backend. Drafts are separate for the new session and each persisted session. A new session, first message, and first agent run are persisted together only on send, so navigation has no empty sessions.

Session switching updates navigation immediately, closes the mobile drawer, and replaces stale transcript and composer content with skeletons. Session loading is independent of provider, integration, approval, and tool bootstrap, which continue in parallel. Stale requests are cancelled and cannot overwrite a later session's transcript or active run.

Session detail loads the latest 20 complete user-anchored conversation turns. Approaching the top of the virtual transcript automatically prepends older cursor pages while preserving the visible scroll anchor. Refreshes merge the latest page into already loaded history, and message deep links continue loading older pages until their target is available. Canonical database history remains complete; pagination limits only browser transfer and reactive state.

The UI must remain usable on desktop and mobile in both light and dark mode.

## Runtime Data

The development stack uses named volumes:

```text
app_data -> /data
db_data  -> /var/lib/postgresql/data
```

Additional named volumes hold Python and frontend dependencies. The repository is mounted at `/workspace` for HMR.

The production Compose stack starts the `matoloop-agent` service with exactly `MATOLOOP_AGENT_DATA:/data` and `MATOLOOP_AGENT_HOME:/workspace`. The production environment template sets these host paths to `/opt/matoloop-agent/data` and `/opt/matoloop-agent/home`; Compose retains the former relative fallbacks for existing deployments. The development service additionally mounts the source tree and a disposable dependency volume. Agent configuration is `/data/config.json`; credentials and durable state also remain below `/data`. These paths are not backend-managed storage. The backend does not migrate or delete agent home contents. Interactive pairing asks for the backend WebSocket URL, computer ID, and one-time token. Non-interactive pairing requires the complete `MATOLOOP_AGENT_BACKEND_URL`, `MATOLOOP_AGENT_ID`, and `MATOLOOP_AGENT_PAIRING_TOKEN` set. Old environment aliases are unsupported. The container currently runs as root, so these mounts and deployment policy, not MatoLoop model policies, define its operating-system scope.

Deleting a deactivated account removes its relationally owned records and backend session trees. Database deletion revokes the backend's `ExecutionAgent` records and credentials, but the backend does not erase files, caches, durable agent state, or configuration on any MatoLoop Agent, including the bundled Compose agent, nor data already written to an external service. Operators must remove those separately. Shared instance resources and credentials remain because they have no user owner.

The production stack uses the two application bind mounts and adds the MatoLoop Agent `/data` and `/workspace` mounts. `docker-compose.no-agent.yaml` is the production alternative without the agent service or its settings:

```text
/opt/mato-loop/data -> /data
/opt/mato-loop/db   -> /var/lib/postgresql/data
```

The production SPA is served by the MatoLoop container together with FastAPI. The development stack keeps separate frontend and backend processes for HMR. The production stack is not used for development work.

## CI and Release Boundary

Forgejo Actions verifies changes and publishes OCI images and Forgejo releases; it never deploys MatoLoop or accesses deployment storage. Pull requests build without secrets, feature branches retain no images, `develop` has one mutable image tag, an immutable `sha-<12>` tag per accepted commit, and short-lived native Linux amd64 MatoLoop Agent artifacts, while releases from `main` have immutable version tags plus mutable `latest`. Both application images currently target `linux/amd64`; stable native archives are not published yet. Runner isolation, variables, release tags, and operator rollback are defined in [ci-and-releases.md](ci-and-releases.md).
