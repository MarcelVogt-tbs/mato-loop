# Architecture

Trust, memory, and dreaming boundaries are described in [memory.md](memory.md). User-authored skill storage, run selection, isolated building, approval, privacy, and budget contracts are described in [skills.md](skills.md).

MatoLoop is a provider-neutral monorepo. FastAPI provides REST and SSE interfaces; the Quasar SPA consumes only this API.

## Layers

- API: HTTP contracts, authentication, and dependency injection
- Services: transactions and application logic
- Agent: provider-neutral model and tool loop plus host policies
- Execution: outbound Python agents for selected workspace, process, and static local-integration operations
- Providers: replaceable LLM and search transports
- Memory: current-session context plus trust-filtered durable and prior-session retrieval
- Embedding: local Infinity transport and asynchronous durable-memory and episode indexes
- Persistence: SQLAlchemy models, Alembic migrations, and settings documents
- Frontend: presentation, user interaction, and localization

## Configuration Boundaries

Bootstrap and infrastructure values come from environment variables. Operational settings are stored as typed Pydantic documents in the PostgreSQL `settings` table.

Additive settings fields have Pydantic defaults. Settings documents declare global or user scope. Global documents use `settings.user_id IS NULL`; user-scoped documents are loaded and stored with an explicit `user_id`. Partial unique indexes enforce the two namespaces separately. Background processing derives user scope from persistent session ownership and never uses an implicit request user. API keys and OAuth tokens are referenced by ID from the separate `credentials` table instead of being stored in settings JSON. Credential payloads are encrypted; the Fernet key is created under `/data/secrets/credential.key` on first use.

Infinity is host-controlled local infrastructure, not a selectable LLM provider. It is reachable only inside the Compose network and computes query, durable-memory, and prior-session message-chunk embeddings with a pinned multilingual model. pgvector stores this derived data in PostgreSQL beside canonical memories and messages. Backend availability does not depend on Infinity and falls back to PostgreSQL FTS. Ownership, current-session exclusion, trust, and retrieval filters are applied in SQL before vector limits; the local embedding service may process both trust levels but never grants visibility.

## Provider Boundary

Provider adapters transport model messages, tool schemas, tool choice, text deltas, and tool calls. They never execute tools or manage sessions and file permissions.

- `openai-codex` uses the ChatGPT device-code flow suitable for self-hosted interfaces and isolated Codex Responses and image-generation transports. Login requires neither a public callback URL nor a local callback port.
- `openai-compatible` supports Chat Completions and Responses API.
- `lemonade` uses Chat Completions and the native image, speech, audio, and transcription endpoints of a Lemonade server.
- Every adapter implements the same internal provider contract.
- The direct ChatGPT Codex endpoint is not a public OpenAI Platform API and remains encapsulated in its adapter.

Technical provider responses are logged server-side and mapped to safe domain errors such as `provider.authenticationFailed`, `provider.rateLimited`, or `provider.unavailable`.

Providers and models have a one-to-many relation in typed AI settings. OpenAI-compatible providers synchronize model IDs through `GET {base_url}/models`. ChatGPT Codex uses its OAuth credential with the private catalog at `GET https://chatgpt.com/backend-api/codex/models`; the adapter adds the native `openai-codex/gpt-image-2` media model with `image_generation` and `image_editing` and keeps the private Codex contracts encapsulated. Credentials never leave the backend. External OpenAI-compatible model IDs remain opaque strings; Codex slugs use the `openai-codex/` namespace. Newly discovered models start disabled except host-declared native media companions, while manually added models provide an explicit fallback.

Lemonade synchronizes installed models only and maps documented labels and recipes to the provider-neutral capabilities `chat`, `image_generation`, `speech_generation`, `audio_generation`, and `audio_transcription`. Image input, tool calling, and parallel tool calls remain separate chat runtime properties. Media resolution first uses an active model with the requested executable capability, then a native media model from the active provider, and finally the explicit global capability default. Image editing reuses the image-generation default only when that model also advertises `image_editing`; it has no separate default setting. Media-only models never appear in chat, compaction, title, or dreaming selectors. Omni collections are not offered because their server-side tool loop would bypass MatoLoop permissions and persistence. Unknown recipes are not inferred from model names. Lemonade image generation omits an unspecified size, step count, and CFG scale so server-side model defaults remain effective; the discovered `Z-Image-Turbo` model therefore keeps its catalog defaults instead of receiving a host-imposed `512x512` size. Every media tool has a host-controlled timeout, 300 seconds by default. Provider timeouts are reported separately from other availability failures as `provider.timeout`, including the timeout and retryability for agent and direct API callers; technical details remain in safe server logs.

Every LLM provider has a required `public` or `private` trust level. A model can override it in either direction or inherit it with `null`. The backend returns both the stored override and effective value. Starting an agent run persists model ID, display-name snapshot, effective trust, and effective pseudonymization. The snapshot keeps history understandable after model rename or deletion. Session selection and provider or model policy changes therefore affect only the next run. User, assistant, and tool messages inherit the trust level of their run. Sessions have no aggregate trust level; normal chat text remains available after a model switch, while memories, tool results, and attachments use their own persisted provenance.

Local identifier and secret protection is enabled by default for effectively public models. Independent Presidio recognizers detect email addresses, IP addresses, phone numbers, IBANs, and credit-card numbers with checksums and specialized validators to limit false positives. `detect-secrets` adds structured API keys, tokens, secret assignments, and private keys. Free entities such as people, places, organizations, product names, and technical terms are not modified. Detected values become random request-scoped markers; text deltas, reasoning summaries, and tool arguments are restored before local persistence. A host instruction tells the provider to preserve markers exactly. Unknown markers from the current request abort processing before tool arguments can be used. Mapping and nonce exist only in memory for one request. Opaque continuation data is neither replayed nor persisted in this mode because it cannot be inspected locally. Images and binary data have no separate content pseudonymization. Detection is best effort and does not guarantee recognition of arbitrary confidential statements or source code. Disabling it deliberately sends released context unchanged to the public provider.

Discovery does not replace local configuration. Known models keep their internal UUID, enabled state, and runtime values. Missing discovered models are marked `missing` and removed from effective selection, not deleted. A failed synchronization leaves the last valid state unchanged. Effective model availability requires global AI enablement, an active provider, an active model, current discovery availability, and an existing Codex connection where applicable.

AI settings define separate defaults for agent runs, context compaction, and title generation. Only available tool-capable chat models can be agent defaults or session models; compaction and title generation remain tool-free internal requests. Session selection overrides the agent default. Without a compaction default, compaction uses the session model and finally a deterministic summary. Without a title default, title generation uses the session model or agent default; a failed model request leaves the locally derived title from the first user message. Invalid default references are removed when the model catalog changes.

## Integration Boundary

Integrations are configured instances of a capability and a host-registered adapter. Every instance has a stable ID, enabled state, optional credential reference, and typed provider-specific configuration in the global `IntegrationSettings` document. Configuration can activate only known adapters; external services provide no executable code, unchecked tool schemas, or prompt text.

Every adapter has a static `backend` or `agent` execution location. Backend adapters cannot be assigned to an Execution Agent. Each agent adapter is bound to one configured agent and is offered only when that agent is the immutable executor snapshot for the run and advertises the host-known operation. Multiple Execution Agents and one local integration instance per adapter kind and agent are supported; models never select an execution location per call. See [integrations.md](integrations.md).

An adapter can contribute statically known tools, controlled prompt fragments, or values for explicitly declared host configuration fields. Before each model request, available tools form an immutable effective tool set. The same binding snapshot exports the schema, validates returned calls, and executes them; calls not offered are rejected. Host tool options do not become model arguments. Security-relevant configuration is reloaded immediately before an external effect. See [integrations.md](integrations.md).

The integration policy core is domain-neutral. Adapters declare host actions, stable shared tools, typed arguments, and one resource level under an integration instance. A resource may narrow the adapter-declared capabilities that apply to it; remote data cannot add capabilities. `ToolSettings` resolves global, instance, and resource policies through one backend resolver. `disabled` denies, `ask` uses the persistent approval loop, and `auto` skips only that approval. Remote ACLs can only remove statically known capabilities. Exact operation grants remain separate from broad policy targets. CalDAV uses this to expose calendar and task-list resources from one account; future mailbox, repository, or device integrations must reuse it rather than add domain policy tables or runtime dispatch branches.

## Agent and Tools

Static host-controlled prompts, repair instructions, prompt fragments, tool descriptions, schema descriptions, and model-facing markers use simple English. Contracts remain concise, explicit, provider-neutral, and free of redundant or contradictory instructions so medium-sized local instruction models and cloud models use the same text. Dynamic user, identity, memory, source, and tool data may use any language; exact German UI labels can appear as quoted product identifiers.

The shared tool prompt requires one compact standalone search query for exactly one information need. It prefers discriminative terms over sentences or task descriptions while retaining essential relationships and exact identifiers. Queries must not combine separate questions, synonym lists, or alternative formulations. If the model chooses a tool, it emits the call in the same response and does not announce future tool use without that call. Current searches normally omit a year; when a freshness year is required, it comes from the frozen local run timestamp rather than prior knowledge. Explicit user years and years in exact names, versions, historical scopes, and comparisons remain unchanged. The `web_search` schema describes only the form and purpose of its sole `query` argument. MatoLoop never rewrites search queries.

The backend agent runner owns the provider-neutral model and tool loop. No-key metasearch and SearXNG remain backend operations; workspace operations are dispatched to the run-bound Execution Agent. Providers never execute tools.

## Execution Agent Boundary

The backend remains authoritative for provider communication, the LLM and tool loop, static schemas, argument validation, policies, approvals, grants, sessions, memory, credentials, backend integrations, session storage, and canonical tool results. A standalone Python Execution Agent connects outbound over an authenticated WebSocket and owns only its configured workspace roots, configured process and shell execution, a disposable session-file cache, and statically declared local integration operations. It receives bounded authorized operations, not the system prompt, chat history, provider credentials, or permission authority.

Execution Agents pair through a bounded one-time registration token. The agent generates its durable access key locally and submits only its SHA-256 hash; after pairing, only that durable key can authenticate WebSocket and transfer requests. Unpairing commits the credential removal before closing the live connection and revoking unclaimed transfer tickets. Existing durable bearer keys can migrate through the same pairing endpoint without invalidating deployed agents.

A session stores mutable preferences for Execution Agent, advertised root, and relative working directory. Starting a run snapshots the agent ID and revision, root ID and revision, working directory, and advertised operations. Preference changes affect only later runs. Disconnects do not switch to another agent or the backend, and dispatched operations are not automatically retried or redelivered. Without a selected and connected agent, normal chat and backend tools continue to work while workspace, process, and agent-local integration tools are unavailable.

File roots retain one model-facing contract:

```text
root=session   -> backend session storage
root=workspace -> selected Execution Agent workspace
```

The backend mediates cross-root and user-facing file transfers with short-lived, owner-bound HTTP tickets. Both sides enforce size limits and validate byte count and SHA-256 before accepting content. The agent's sparse session cache contains only files used by authorized operations, is size-bounded with oldest-file eviction, and validates size and SHA-256 on every hit. It is never canonical and may be cleared without losing session data.

`process.exec` exposes only configured executable aliases; `shell.run` exists only when an exact shell executable is configured. Both run with a bounded environment, timeout, cancellation, and output limits, but neither is an operating-system sandbox: the workspace working directory does not constrain process filesystem or network access. Every call therefore offers only `allow_once` or `deny` and displays this warning. Linux and Docker are the currently tested execution environments.

The tool harness follows the OpenCode pattern: a central registry connects a stable name, short model description, typed Pydantic input model, and asynchronous handler. Every handler receives a `ToolContext` with run and session plus `Context.ask` for permission requests. The runner has no tool-specific dispatch branches. Unknown, unavailable, or schema-invalid calls return structured tool results.

`max_tool_calls` is a cumulative emergency ceiling for all attempted tool calls in a run; its default is 50. Every model request receives the used and remaining budget, and every call in a parallel batch consumes one slot. A batch larger than the remaining budget is rejected before any tool in that batch executes. After the last allowed call succeeds, the host removes all tool schemas and permits one tool-free finalization request, including when this requires one request beyond `max_steps` and the model-request budget still permits it; the model must identify requested actions not confirmed as completed. Calls returned despite an empty tool set still fail with `agent.toolCallLimitReached`. In `available` and `required`, `max_research_tool_calls` additionally limits the combined sum of `web_search` and `webfetch`; the additive default is eight. Failed and denied calls are identified by tool name and canonical sorted argument JSON. Repeating the same failed call persists a structured error and terminates the run rather than repeating approval, error, or retry loops. A failed mutating tool remains unresolved until the same tool succeeds; subsequent model text is held and cannot finalize as an unconfirmed success. Permission denial is already a confirmed negative outcome and does not require a corrective mutation. Repeating an already successful research call returns compact `alreadyCompleted` output without network access; the following normal request receives no research tools and can finalize from existing evidence.

System prompt and tool schemas are derived from the same effective tool set for every model request. Every host-installed built-in and statically declared integration capability also appears in a compact model-facing catalog when it is not callable. Catalog entries contain only controlled names, grouped availability reasons, and activation guidance; they carry no schema, arguments, external labels, credentials, or permission effect. The prompt explicitly forbids calls to catalog-only capabilities. Full schemas and tool-specific file, memory, media, webfetch, and identity instructions remain limited to callable tools; immutable host and trust rules remain. Cross-tool policy lives in the system prompt, invocation shape lives in schemas, and the same rule is not repeated across both merely for emphasis. Image prompt profiles are static host text selected after final tool filtering by the resolved `(adapter_type, provider_model_id, tool_name)` target. The effective tool snapshot binds that target; a target change before execution returns `tool.unavailable` so a later step can rebuild the prompt and schema together. The initial profiles cover GPT Image 2 generation and editing plus `Z-Image-Turbo` generation. During the initial `required` search gate, the model sees only `load_skill` when a catalog is available and `web_search`; loading one clear skill first does not satisfy the required search. Text and reasoning from that gate are neither persisted nor streamed. The host removes only annotative `title` fields from Pydantic JSON schemas and preserves descriptions, required fields, enums, defaults, limits, and `additionalProperties: false`. A deterministic production-sized budget test guards the combined static prompt and built-in tool schema envelope. Local time is frozen at run start so relative dates stay consistent across tool rounds and the prompt prefix does not change merely because time passes.

Skills are bounded user-scoped instruction records, not executable extensions. A run snapshots the catalog, selects at most one skill from the latest request by exact ID, and exposes its instructions only after an exclusive `load_skill` call. Explicit chat creation delegates a compact brief to an isolated builder request containing only the latest request and effective schemas, then imports a strict editable session draft only at an approved exact SHA-256 revision. Skills cannot add schemas, handlers, credentials, or permissions; model trust, pseudonymization, and shared request, tool, and context budgets continue to apply. See [skills.md](skills.md).

`web_search` is available without an integration and defaults to built-in no-key metasearch. It is configured only through tool settings and is not an `IntegrationInstance`. Every active SearXNG integration adds a stable UUID-based provider key. `ToolSettings.web_search` chooses the primary provider and optional fallback; the model supplies `query` and may select `search_type=images` when an exact visual reference is needed. Image results include a direct `imageUrl`, which must pass through `webfetch` before use. When SearXNG reports failed default engines with no results, MatoLoop retries once on the same instance with `bing`, `mojeek`, and `presearch`. Fallback must differ from primary and is used only after remaining network errors, timeouts, HTTP 408, HTTP 429, HTTP 5xx, or unavailable engines. Disabling or deleting a selected instance falls the primary back to no-key search and removes an invalid fallback. The no-key client `ddgs` selects public search backends automatically. Results are deduplicated by canonical URL and include title, URL, discovery snippet, and publication date.

Search providers deliver discovery metadata only. MatoLoop streams at most 256 KiB from SearXNG, normalizes snippets locally to bounded plain text, and uses one deadline for primary, recovery, and fallback. `webfetch` applies one global configurable response limit to declared, streamed, and decompressed content. It prepares pages entirely locally: Markdown and text prefer semantic main content, relative links resolve against the final URL, and active markup is removed. PDF text is extracted locally with page markers. Pages without extractable text are rendered to bounded transient JPEG images and read in batches by the active image-capable chat model or the configured default vision model. Selecting a public vision default is an explicit release decision, so helper selection does not apply an additional trust filter. These helper calls consume the agent model-request budget. Its structured result includes input content type, actual output format, and final HTTP status. Non-success HTTP status is returned only as controlled `webfetch.requestFailed` with `statusCode`; external error text and response bodies remain hidden.

Sessions control research with `required`, `available`, or `disabled`. `disabled` removes `web_search` and its prompt instructions; independent `webfetch` still follows its policy. `available` runs the normal research-capable loop with automatic tool choice. `required` adds only an initial gate: the first successful `web_search` in the current user turn is forced by offering only `web_search` with `tool_choice=required`. Text and reasoning from this phase are neither persisted nor streamed; call and result are canonical. Failed or invalid calls use a bounded semantic retry budget distinct from transport retries. A technically successful search with zero results satisfies the gate. Afterward, `required` uses exactly the normal `available` loop.

Both research modes give the same best-effort citation instruction. The model places visible Markdown links to exact current-turn research URLs immediately after supported claims, with at most two links per claim. The host does not rewrite answer text. Research metadata stores only effective policy, whether research occurred, and which current research URLs are visibly linked. The frontend canonicalizes normal Markdown links against this allowlist and displays matching inline source chips. This is display and audit data, not proof that a source was used or supports a claim.

Search snippets are for discovery. Exact prices, availability, compatibility, variants, and specifications require fetching the concrete page. Similar model codes must not be merged. Legal, tax, regulatory, medical, financial, safety, and other consequential claims prioritize official or primary sources. Consequential claims, exact values, thresholds, procedures, and recommendations should be checked against evidence for the requested jurisdiction and effective date or version. Missing or conflicting evidence requires qualification or omission; current rules must not be applied to historical periods without verification, and numeric outcomes require necessary inputs and calculation. Empty search or unsuitable links create no special final block after the required gate; normal finalization decides whether to call more tools within shared budgets.

Every normal agent request includes current local time after optional pinned and retrieved durable memories and prior-session episodes. The configured `GeneralSettings.default_timezone` supplies an unambiguous ISO timestamp with UTC offset, and the host adds the English weekday to avoid model calendar arithmetic. The prompt explains that the timestamp resolves relative dates but does not make prior knowledge current. Specialized dreaming, compaction, and title requests do not receive this time context.

Global webfetch policy is `disabled`, `ask`, `auto_public`, or `auto_allowed`, defaulting to `auto_public` for new configurations. Public targets are fetched automatically; private and loopback targets require approval. Models may override the policy but cannot bypass the global tool switch or network allowlist. Ask mode uses an exact SHA-256 matcher over the complete canonical URL. Persisted display URLs contain no query values; redirects are reauthorized before DNS and HTTP.

Message-owned files use one generic asset contract. PostgreSQL remains authoritative for owning message, order, trust, lifecycle, purpose, MIME type, size, SHA-256, controlled metadata, and session-relative path; file bytes live only in the session tree. `purpose=attachment` identifies user-supplied conversation inputs and `purpose=artifact` identifies byte-backed outputs returned by tools. Pure JSON, status, query results, and embedded content generated inside assistant Markdown remain relational message content. Tools that only read or mutate an existing session or workspace file retain a host-derived path reference instead of creating a duplicate snapshot. User uploads live under `attachments`, visible generated tool artifacts under `generated`, downloaded originals under `downloads`, and required media-processing derivatives under `derived`. Persisted paths retain UUID-owned directories. The session API returns authenticated URLs, never physical paths or Base64. Asset writes are immutable, quota checked, atomically published, and compensated when relational persistence fails. Undo and retry remove assets owned by deleted messages; session deletion removes the complete tree, while already executed file operations remain effects rather than message assets.

Validated PNG, JPEG, WebP, and GIF originals use the general 64 MiB file limit. Before provider transport, images larger than 5 MiB or 2048 pixels on either edge are converted in memory to bounded JPEG copies; persisted originals remain unchanged. MP4 and WebM videos are validated by container probing and bounded to 64 MiB and 15 minutes. WAV, MP3, M4A/AAC, Ogg/Opus, FLAC, UTF-8 text, PDF, DOCX, XLSX, and PPTX uploads are processed within bounded size, duration, and extraction limits; other files remain safe download and copy assets. Originals and derivatives share a 500 MiB session quota. Remote PDFs fetched as research sources remain canonical webfetch text results rather than session assets unless a tool explicitly returns a downloaded file. Normal context projection materializes only current or explicitly referenced media for capable models and retains its trust boundary. Direct helper inputs for explicitly configured vision, video, and transcription defaults are the exception: choosing those defaults is the user's release decision. Text projection and compaction markers retain asset ID, filename, and session-relative path so `session_read` can recover historical assets. This hybrid asset model is storage, not another session-memory system: complete message chronology and non-file tool results remain canonical in PostgreSQL.

The always-available `generate_qr_code` and `read_qr_code` tools run locally and never call a media provider. Generation encodes at most 2,000 UTF-8 bytes exactly into a deterministic PNG with a standard quiet zone; persisted tool-call history redacts that content. Reading accepts only a verified current-session image attachment, returns up to 16 text payloads, and propagates the source message trust level. Empty scan results are normal successful results. Generic image generation explicitly excludes QR and other machine-readable codes.

Media tools `generate_image`, `edit_image`, `generate_speech`, `generate_audio`, `transcribe_audio`, and `analyze_video` are capability-bound registry entries. Each capability has global `disabled`, `ask`, or `auto` policy reloaded before every call; image editing and video analysis default to `ask`, while the other additive media tools default to `disabled`. `analyze_video` accepts only an explicit `session` or `workspace` root, a relative path, and an optional language. Managed session assets retain attachment provenance and are verified against their persisted size and SHA-256 hash before analysis. The configured video-analysis model may support either native video input or image input for the bounded frame fallback. Selection prefers active native video, configured native video, active image input, configured video-analysis image input, and finally the general vision default. This switches away from the active model only for an additional input capability. Frame models return chronological prose; the host records sampled timestamps separately instead of requiring models to reproduce them as structured data. The configured transcription model handles audio that the visual model cannot consume. Configured helper-model selection ignores source and target trust because choosing a public vision, video, or transcription default is an explicit user release decision; result provenance still retains source trust. Provider and model selection, probing, extraction, and sampling remain host-controlled and are not model tool arguments. Helper calls consume the agent request budget. Image generation binds approval to the session and resolved provider, model, and trust level. Image editing additionally binds the exact source attachment IDs, accepts one to five ordered current-session images with a combined 20 MiB limit, and never sends private sources to a public target. `auto` skips approval only. The model-facing edit contract asks for a standalone prompt with explicit changes and invariants; the host does not rewrite it. Edits use the native Codex JSON endpoint, create a new validated attachment, preserve originals, and record source, provider, model, and trust provenance. They are independent of workspace write mode because they do not mutate session files or workspace paths. A private media source or target makes its tool message private. Direct authenticated upload transcription is an explicit user action and needs no agent approval, but follows the same transcription policy and model resolution.

The model-facing image contracts default generated prompts to clear English while preserving exact prompts, quoted visible text, and proper names verbatim. GPT Image 2 generation uses a stable brief order and avoids unsupported creative expansion. Its edit profile puts the base target first as Image 1 and expresses localized work as a labeled delta contract: Image 1 remains the same base scene, additional images have narrow reference roles, and unchanged canvas, aspect ratio, crop, framing, camera, perspective, geometry, identity, text, and unrelated content are explicit invariants. Only nearby shadows, reflections, and occlusion may change when needed to integrate the requested edit. Intentional global transformations preserve all unrequested structure and identity. The `Z-Image-Turbo` profile requests a fluent natural-language scene description rather than keyword tags. No hidden provider prompt rewrite occurs; adapters send the resulting tool argument unchanged.

Video analysis accepts host-bounded `speech`, `overview`, and `fine_grained` modes and an optional analysis objective. Speech mode extracts and transcribes audio without sending video or frames to a chat model. Overview sampling targets five-second intervals up to 32 frames; fine-grained sampling targets two-second intervals up to 64 frames. Native video transport is limited to 50 MiB and larger inputs use frame analysis when available. Frame fallback sends up to four ordered images in one multimodal user message, requests at most 300 words, and limits compatible providers to 1,024 output tokens. Audio is converted to mono 16 kHz WAV and split into at most 120-second transcription requests. The host assigns complete visual time ranges, aligns transcript segments with those ranges, and returns `visualSegments`, `transcriptSegments`, sampled timestamps, audio status, and `audioQuality: not_assessed`; models do not determine segment timing or recording quality. Video analysis defaults to a 1,800-second overall timeout.

Agent file tools retain roots `session` and `workspace`. Arguments separate root from a relative POSIX path; `.` means the root and the technical prompt forbids root names in paths. The backend serves the session branch and a run-bound `ExecutionClient` serves the workspace branch. Both reject absolute paths, parent segments, and symlink traversal. Session storage exposes flat `files`, `attachments`, `generated`, `downloads`, and `derived`. Asset directories are readable and may be copy sources, but are never move sources or destinations and never write, copy, or delete destinations. Only `files/...` is mutable. Successful regular-file writes, copies, and moves persist a host-derived action reference on the tool result; directories and failed or denied actions do not. The session API strictly validates these references and derives authenticated download URLs without trusting stored URLs. `provide_file` turns a successful read-authorized regular-file lookup into a host-generated chat download reference without reading or copying the content and is needed only for an existing file not already exposed by a successful write, copy, or move. Session references remain bound to that session; workspace references retain the original agent, root, and working-directory identity even if the session preference later changes. Download requests recheck user ownership and resolve the current file through the same boundaries, so changed content is served while deleted or moved paths fail safely. Tool exceptions become structured error codes and are not exposed raw to models or clients.

The authenticated file explorer has a workspace scope and a session scope. Workspace scope requires the session's selected, connected Execution Agent and advertised root; unsent session drafts pass those preferences explicitly. Session scope is ownership-bound to a persisted session and exposes the same five directories as agent tools, with mutations restricted to `files/...`. Explicit user uploads and empty `.txt` or `.md` creation accept arbitrary bytes, are limited to four sequential requests of 64 MiB each, use no-replace atomic publication, and retain the session-wide quota. Preview classification never trusts an uploaded media type: decoded PNG, JPEG, WebP, and GIF images up to 5 MiB use controlled image responses, while UTF-8 text and Markdown up to 1 MiB stay escaped or sanitized. Static self-contained SVG previews are also limited to 5 MiB and reject DTDs, entities, scripts, event handlers, animation, foreign content, processing-instruction stylesheets, and non-fragment resource references before delivery with a sandboxed SVG-specific CSP. Other files use forced `application/octet-stream` downloads with `nosniff`, same-origin, no-store, and sandbox headers.

The authenticated shell has no global top bar. Its branding and close control live in the sidebar on every viewport; a 48-pixel floating navigation control appears only while that sidebar is hidden. Pending approvals and active model work share one fixed status slot per session, with approval-required state taking priority. The explorer is a chat-only surface whose floating open control disappears while the file area is visible. At the Quasar `md` breakpoint and above, one stable `QSplitter` keeps the chat mounted beside the file area, gives each panel at least 30 percent of the width, and persists only its bounded local ratio. Below that breakpoint, a maximized `QDialog` hosts the same file area without a splitter. Floating controls overlay the full-height content and add only a conditional inset inside scrollable content. Successful file-mutating tools expose compact view and download actions in their existing timeline header. View uses the integrated explorer viewer with the action's bound root identity and disables all mutations; switching scope returns to the current session or workspace root. The integrated viewer replaces the visible tree while preserving its mounted expansion state; returning restores focus to the opened file when it remains visible. Any existing UTF-8, non-NUL file within the 1 MiB preview limit can be edited as source. Markdown additionally uses a lazy-loaded, telemetry-disabled Toast UI visual mode; image-bearing Markdown remains source-only so editing cannot trigger external image requests. Saves require the SHA-256 revision returned by preview, validate and replace the file under the root operation lock, and return `file.changed` instead of overwriting a concurrent update. Dirty editor state is kept outside the editor instance and guards internal navigation and browser unload. Writable tree entries expose direct rename and delete menus. Rename changes only the basename, uses no-replace filesystem semantics, and clears grants for both source and destination before mutation; delete clears affected grants before mutation. Filesystem mutations serialize with working-directory assignment per user so an active session workspace cannot be renamed or removed concurrently.

Agent runs are persistent and use SSE for text deltas, released reasoning, approval events, and terminal states. Model and provider availability and agent-model tool support are checked before accepting a session or user message; required search remains a runtime check after acceptance. A provider-neutral model turn is usable only when it returns a tool call or non-empty assistant text. Released streamed text is retained when the final transport result omits it; an otherwise empty turn receives one bounded host repair request and a repeated empty turn fails with `agent.emptyResponse` instead of completing silently. Runtime failure atomically persists run state and exactly one structured MatoLoop error response. `run.failed` only accelerates delivery. The response has a language-neutral code and parameters, never enters model context, memory, or dreaming, and survives reload. `run.phase` reports timed phases such as context building, compaction, model request, tool execution, and finalization. Assistant metadata records estimated input size, context preparation, provider duration, and first reasoning or text signal without prompt content. Public reasoning comes only from documented provider summaries, explicit `reasoning_content`, or clearly marked leading think blocks. It is persisted separately and excluded from memory, compaction, and `session_read`. Encrypted provider reasoning remains private continuation state, never reaches the frontend, and is reused only for identical provider, model, credential, endpoint, trust, and pseudonymization scope. Active pseudonymization drops it.

Undo and retry are distinct chat operations. Undo applies only to a user message, cancels an active run if needed, and removes that message plus the complete following suffix. The client first loads its attachments into a local composer draft, then truncates persistent history. Retry applies only to the latest persisted runtime-error response. The preceding user message and attachments remain while the failed assistant and tool suffix is removed and a new run starts with the model, trust, and pseudonymization snapshot of the failed run. Background dreaming never blocks send, undo, or retry. Neither operation reverses already executed tool, workspace, permission, or memory effects; the UI warns before execution.

Assistant answers remain raw Markdown in persistence and render only in the frontend. The canonical assistant format is the Markdown document body itself; a complete response enclosed only by one outer `markdown` or `md` fence is unwrapped before new persistence, and the same normalization applies to API payloads for historical messages. This contract is provider-neutral and keeps transport formatting out of the viewer. The shared Markdown viewer serves chat messages and saved file previews; print output uses the same preview without controls. The viewer disables raw HTML, limits link schemes, and sanitizes generated HTML before DOM output. Fenced code blocks receive source download and copy actions; source text stays outside the rendered DOM in a render-local list referenced by index. Mermaid is an inline Markdown block without separate framing. Completed diagrams receive source copy, sanitized SVG download, and width-independent fullscreen actions without creating a persisted file. An unfinished streaming Mermaid fence shows a controlled progress message. A genuinely closed fence renders immediately even while later answer text continues streaming, and bounded source-and-theme render caching prevents repeated work. Markdown files containing Mermaid fences remain source-only while editing so the WYSIWYG editor cannot rewrite embedded diagram source; their read-only preview still uses the shared viewer.

The agent may use Mermaid without an explicit request only when it materially clarifies complex structure, keeps the essential explanation in text, and does not add decorative diagrams. Mermaid is lazy-loaded, receives no content-controlled configuration, disables HTML labels and interactions, and its SVG output is sanitized again without external resources, active CSS, or active content. Source size and renderer complexity remain bounded. Rejected source and renderer failures map to controlled local categories for empty, oversized, forbidden-configuration, unavailable, and invalid-or-complex diagrams; raw parser errors are never rendered, and source copy remains available. Mermaid source remains only in the persisted assistant Markdown; rendered diagrams and other embedded answer content stay local and are not materialized as session files. External Markdown images cause no browser request before explicit origin approval scoped to the chat session and frontend instance. The frontend then loads and decodes each concrete URL before showing it. Loading, decoding, and timeout failures remain retryable placeholders. The agent must not invent external image URLs and uses `webfetch` for exact URLs when available; validated internal tool attachments are preferred. Only validated internal attachment routes load automatically. User text, reasoning, and tool results stay outside this HTML rendering boundary.

Mathematical notation in assistant answers renders locally with KaTeX from inline and block LaTeX using dollar and bracket delimiters. KaTeX disables trust-dependent HTML, link, and image commands and limits macro expansion and element size. The sanitizer allowlist contains only required HTML, MathML, and SVG structures; inline styles remain only inside KaTeX-generated subtrees. CSS and fonts ship as local build artifacts.

Saved Markdown files have a standalone authenticated print route outside the application shell. It reloads the bounded preview through the existing workspace authorization context, rejects a changed revision, blocks external images, waits for local fonts, KaTeX, and Mermaid, and then uses the browser print dialog with a light A4 layout. This preserves selectable text and vector diagrams without a server-side PDF engine. A future isolated browser service may render the same route for direct downloads.

Reasoning is collapsed by default. The last selected state is stored in authenticated `UserPreferences` and applies across devices. The UI labels public reasoning as model-provided, not guaranteed complete internal thought.

Run tasks and approval waiters are intentionally process-local. The backend uses one worker. Startup safely terminates active runs and invalidates open approvals; resume and distributed worker queues are out of scope. See [harness.md](harness.md).

## Working Directories and Approvals

Sessions always have their backend session root and may select an Execution Agent, one of its advertised roots, and a relative working directory for `root=workspace`. A missing or disconnected selection makes only workspace and agent-local capabilities unavailable; approval cannot create or replace that root.

Read mode offers only `list_directory` and `read_file`; stale mutation calls are also blocked at execution time. For change requests, the model tells the user to switch the German UI control **Agent-Modus** from **Lesen** to **Schreiben**, rather than denying the capability generally. Write mode also offers `write_file`, `create_directory`, `delete_path`, `copy_path`, and `move_path`. Reads within both host-bound roots are automatically allowed; mutations require write mode. Agent file access never creates an approval that could expand a missing root, read-only mode, or path boundary.

`read_file` reads UTF-8 text by line with one-based `offset`, bounded `limit`, and line numbers. Large files are read in chunks, individual long lines are bounded, and tool output indicates continuation. `list_directory` paginates from offset zero. Copy and move validate source and destination roots before effects; the destination path always names the exact new entry and never overwrites.

Non-file permissions use persistent approval requests. The agent run waits for `allow_once`, `allow_session`, or `deny`; the request remains an inline chat card until decided.

Permissions use resource-specific matchers. File scopes contain root type, host-bound root identity, and relative POSIX path; legacy global path scopes are rejected. URL access compares exact hashes of complete canonical URLs, session access compares UUIDs, and session discovery uses a separate collection scope. `session_read` can read the current session without approval; another session requires an exact `session.read` grant or approval. `session_tool_result_read` reads only a known tool message in the current session without approval. `session_browse` and `session_search` share the `session.search` capability and collection grant. Discovery releases only a bounded preview; canonical transcript windows still require `session_read`.

## Context and Compaction

The shared agent identity is a user-scoped `AgentIdentitySettings` document separate from memory and work modes. Name and identity instructions are loaded once per normal run and projected below immutable host rules. The host-controlled `update_agent_identity` tool follows global `disabled`, `ask`, or `auto` policy; see [agent-identity.md](agent-identity.md).

Complete message history remains canonical in the database. Before every model request, the context manager creates a transient projection from the system prompt, trust-visible pinned and retrieved durable memories, bounded prior-session episodes, an optional summary, and recent original history. Private cross-session content never reaches effectively public models. The same applies to private messages returned through session tools; normal current-session chat history remains and can be locally pseudonymized. Tool call and result remain a pair, interrupted calls receive terminal errors, and tools are never re-executed during projection. Before the latest user turn, prior web searches retain source ID, title, URL, and publication date while other tool output becomes a structured `toolResultReference`. `session_tool_result_read` retrieves canonical content in fixed 12,000-character chunks. Current-turn tool output uses a cumulative budget: small results stay complete and remaining space is shared fairly among larger results. Search snippets and webfetch content are shortened inside valid JSON envelopes. Canonical provenance and retrieval remain available without adding complete pages and large tool results to every prefill.

Context window, maximum output, characters-per-token estimate, and tool, parallel, streaming, and image capabilities are configurable per model. Discovered models store the latest provider value separately from the effective window. New discovered models follow the provider value automatically; manual override stops automatic updates and can later return to provider value. If no provider value exists, the conservative fallback is 128,000 tokens. Existing persisted values remain manual overrides.

Current tool output has no fixed token cap. After any required compaction, the context manager subtracts system prompt, tool schemas, summary, conversation, images, and historical tool references from the model-dependent compaction threshold and shares the remainder among current tool outputs. Markdown and text are shortened near block boundaries while search and webfetch envelopes remain valid. Canonical results are unchanged. Historical tool output keeps a separate compact reference budget.

Input budget reserves output and safety tokens. Every request projection is checked against the effective window of the model frozen for the run. Switching to a smaller model therefore triggers compaction before the next agent request when needed. Compaction summarizes only user and assistant chat text from a completed older prefix into a persisted `context_summaries` generation; tool calls, tool results, and attachment metadata are excluded. An existing summary can be compacted again at the same boundary. The configured compaction model falls back to the active model and finally a marked deterministic summary. Projection and compaction never edit or delete original messages; only explicit undo or retry removes its defined suffix.

After the first message is persisted, the agent run and a separate tool-free title request start concurrently. The agent task is scheduled first; title generation uses only the first user message and never blocks the run. The title inherits that first user message's trust level dynamically; manual renames retain the same classification. `chat_sessions.title_generation_status` persists `pending`, `running`, `completed`, `failed`, or `skipped`. Only `running` with an unchanged local initial title permits final update. Manual rename sets `skipped` and wins races. Successful titles publish `session.title.updated`; status-based frontend polling remains a reconnect fallback. The first output line is limited to 80 characters. Empty or reasoning-only output receives one repair attempt with a provider-neutral output budget increased up to a host maximum of 4,096 tokens. Reasoning is never used as title. Provider failures, invalid second output, cancellation, and orphaned `running` states found at startup end as `failed`; the local title remains. Existing sessions were migrated as `skipped`.

## Error Contract

API, SSE, tool, and persistent chat errors use one descriptor with stable code, controlled English fallback, and optional structured data:

```json
{
  "error": {
    "code": "validation.tooShort",
    "message": "The value is too short.",
    "field": "password",
    "params": {
      "minLength": 10
    }
  }
}
```

Required fields and channels:

- `error.code`: stable code for program flow and localization
- `error.message`: controlled English fallback for channels without localization
- `error.field`: optional affected input field
- `error.params`: optional values for dynamic text
- HTTP status: general failure class and fallback

English fallback text comes only from the central backend catalog. Pydantic details, exception text, and external provider responses never reach clients. Unknown syntactically valid codes remain intact with the safe `The action failed.` message.

The frontend localizes codes centrally in `apps/frontend/src/utils/api-errors.js` and always prefers the German translation over `error.message`. An Axios interceptor displays API failures as negative Quasar toasts. Persistent agent failures appear as MatoLoop chat responses and do not create a duplicate domain toast. Unknown codes use a safe frontend fallback based on HTTP status. Other channels may use `error.message` directly or localize `error.code` and `error.params` themselves.

## Frontend Interaction

Quasar components form the primary UI layer. Pinia stores hold server state; components coordinate presentation and user action.

Destructive actions use `useConfirm` or `v-confirm`. More complex input and approval decisions use Quasar dialogs. Success messages appear at the initiating UI point; API failures are notified centrally only.

Unsent chat text is a browser-local draft and never reaches the backend. Drafts are separate for the new session and each persisted session. A new session, first message, and first agent run are persisted together only on send, so navigation has no empty sessions.

Session switching updates navigation immediately, closes the mobile drawer, and replaces stale transcript and composer content with skeletons. Session loading is independent of provider, integration, approval, and tool bootstrap, which continue in parallel. Stale requests are cancelled and cannot overwrite a later session's transcript or active run.

The UI must remain usable on desktop and mobile in both light and dark mode.

## Runtime Data

The development stack uses named volumes:

```text
app_data -> /data
db_data  -> /var/lib/postgresql/data
execution_agent_data -> /data in the Execution Agent
```

Additional named volumes hold Python and frontend dependencies. The repository is mounted at `/workspace` for HMR.

The standard Compose stacks start the Execution Agent and mount `MATO_EXECUTION_AGENT_WORKSPACE` at `/workspace`. `MATO_EXECUTION_AGENT_CONFIG` selects the runtime JSON configuration mounted as `/config/config.json`; connection values are not runtime settings. Interactive pairing asks for the backend WebSocket URL, computer ID, and one-time token. Non-interactive pairing requires the complete `MATO_EXECUTION_AGENT_BACKEND_URL`, `MATO_EXECUTION_AGENT_ID`, and `MATO_EXECUTION_AGENT_PAIRING_TOKEN` set. The agent waits while unpaired and stores the URL, ID, and generated credential under `/data/agent-state`. The backend data volume is not mounted into the agent.

The production stack uses two application bind mounts and adds the configured Execution Agent workspace and configuration mounts. `docker-compose.no-agent.yaml` is the standalone production alternative without the agent service or its settings:

```text
./data -> /data
./db   -> /var/lib/postgresql/data
```

The production SPA is served by the MatoLoop container together with FastAPI. The development stack keeps separate frontend and backend processes for HMR. The production stack is not used for development work.

## CI and Release Boundary

Forgejo Actions verifies changes and publishes OCI images and Forgejo releases; it never deploys MatoLoop or accesses deployment storage. Pull requests build without secrets, feature branches retain no images, `develop` has one mutable image tag plus short-lived native Linux amd64 Execution Agent artifacts, and releases from `main` have immutable version tags plus mutable `latest`. Both application images currently target `linux/amd64`; stable native archives are not published yet. Runner isolation, variables, release tags, and operator rollback are defined in [ci-and-releases.md](ci-and-releases.md).
