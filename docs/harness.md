# Lean Agent Harness

This document defines the target architecture for the lean OpenCode-inspired agent harness. It complements [architecture.md](architecture.md); its runtime, tool, permission, and context boundaries are mandatory.

## Runtime and Coordinator

MatoLoop manages runs and run-bound agent-action approvals through exactly one process-local run and approval coordinator. The backend therefore uses one worker. The coordinator owns active run tasks and waiters for open agent-action approvals. Persistent background approvals such as `memory_change` do not use a live waiter. The coordinator is neither a distributed scheduler nor a queue and uses no cross-process locks.

- A run continues only in the coordinator that started it.
- An approval decision can resolve only a live waiter in that coordinator.
- Multiple backend workers, parallel coordinator instances, and transfer of a run to another process are unsupported.
- Persistent run state serves API, UI, and audit. It is not a Python stack checkpoint or executable queue.
- Graceful shutdown and process termination must not execute a tool twice.

Agent-action approvals and session grants are persistent, but run restart resume is explicitly not guaranteed. After backend restart, previously active or waiting runs end terminally as interrupted or failed and their open agent-action approvals expire. Deciding a persisted agent-action approval without a live waiter returns `approval.runInactive`; it does not resume the old run or create a grant. The user starts a new run when needed. Fully persisted session grants created before restart remain valid. Persistent `memory_change` approvals are not run-bound, survive restart, and execute through their own transactional resolver.

Approvals and agent questions have no inactivity timeout. A live run waits until the user responds, explicitly cancels the run or deletes the session, or the backend process stops. Browser and SSE disconnects do not resolve or expire these interactions.

This is a deliberate first-version boundary. Restart resume would require persistent tool checkpoints, idempotent execution, leases, and a recovery strategy; it must not be simulated by reloading an `AgentRun`.

User cancellation is an explicit run operation and is never inferred from SSE disconnect. The cancel endpoint requests cancellation of the process-local task and returns immediately; SSE publishes the later persisted terminal state. Repeated calls do not cancel cleanup again. Completed runs return idempotently. Provider streams and child processes are interrupted, and dispatched MatoLoop Agent requests receive a best-effort cancel message. The runtime does not wait for a mutation result: an operating-system file operation that already started may still finish, and its late result is ignored. Successfully streamed text and public reasoning become an interrupted assistant message; without visible output, an empty interruption marker is stored. Hidden output from the initial required-search phase remains excluded. Completed tool effects are not reversed. The run's open agent-action approvals expire and incomplete tool calls receive terminal errors before `message.interrupted` and then `run.cancelled` are published. Graceful backend shutdown is not an explicit user cancellation and creates no such message marker.

## Profile Budgets

Each agent profile stores `maxToolCalls` as a strict positive integer or `null` for unlimited tool calls. Zero, negative numbers, booleans, strings, and fractional values are invalid. The profile editor exposes "Tool-Aufrufe pro Lauf", "Maximale Tool-Aufrufe", and "Unbegrenzt".

| Profile | `maxToolCalls` | `integrationsEnabledByDefault` |
| --- | --- | --- |
| "Allgemein" | `25` | `true` |
| "Plan" | `null` | `false` |
| "Build" | `null` | `false` |
| "Sysadmin" | `null` | `false` |
| Custom profile | inherited from shipped base | inherited from shipped base |

`Allgemein`, `Plan`, `Build`, and `Sysadmin` are independent protected instance bases. Custom profiles store exactly one of their IDs as `baseProfileId` plus sparse typed overrides. Missing fields inherit the current selected-base value; explicit `null`, `false`, empty lists, and empty maps replace it where valid. Integration availability and private/public built-in, integration, and resource permission maps merge by entry so one override does not copy or detach the rest of the base profile.

Normal run creation freezes the selected profile's limit in the input message's private `_matoloop.maxToolCallsByRun` map, keyed by run UUID. Retry adds a new entry from the current profile configuration without overwriting the failed run's snapshot. The former single-value `maxToolCalls` input metadata remains readable and is retained for the failed run when retry creates the map. Children receive the parent's frozen limit, not a newly edited profile value or the parent's remaining balance; each child counts its own calls.

A finite limit covers attempted tool calls, including failed, invalid, denied, and research calls; every member of a returned batch counts individually. If the entire batch cannot fit in the remaining budget, the host rejects every call before any handler executes and persists matching tool errors. Budget exhaustion removes all tool schemas and allows one tool-free finalization request from confirmed evidence, with unfinished work stated explicitly. The final assistant message stores `agent.toolCallLimitReached` as a canonical warning and `completionCause`, so the outcome survives reload and is available to a delegating parent. Calls returned despite the empty tool set are recorded as errors and terminate with that code; an unusable final response still fails normally. Rejection is atomic for dispatch, not a rollback of earlier effects.

The old runtime settings `max_steps` (20), `max_model_requests` (30), `max_tool_calls` (50), and `max_research_tool_calls` (8) are no longer active caps. Main and helper model-request counts, tool counts, research counts, usage, and timing remain metrics rather than independent stopping limits. There is no global elapsed-time or monetary-cost ceiling. Unlimited tool calls do not disable per-request and per-tool timeouts, context/output bounds, bounded semantic and repair retries, repeated-error protection, cancellation, or the four-parallel/eight-total child limits.

Failed calls are tracked by normalized tool name and arguments plus relevant computer context. An unchanged failed repetition is not executed and gets one correction opportunity; a further unchanged repetition terminates unless finite-budget finalization has taken over. A successful mutating action changes preconditions and permits retry, while an unrelated successful read does not clear failed-call protection. Earlier failure evidence remains canonical. There is no same-tool mutation-success gate: an alternative tool may repair the work, or the model may report a blocker without claiming success. An output-truncated tool batch is rejected in full before effects, with bounded repair attempts even for an unlimited profile.

## Native Subagents

The Plan and Build main profiles expose `task` with a `tasks` array of one to four objects containing a short `description` and a complete `prompt`. These are generic assignments, not named agent types. The main runtime starts the children concurrently, waits for all terminal outcomes, and receives one bounded result per child with session/run/message references. One failed child does not discard successful sibling results. A parent run may create at most eight children; children cannot delegate. Each child uses the ordinary runtime limits. There is no background-job API, automatic parent continuation, separate scheduler, or tree-wide token ledger.

Children are ordinary message-backed sessions with immutable `parent_session_id`, `spawned_by_run_id`, `spawned_by_tool_call_id`, and `spawn_index` provenance. They inherit the same owner, project, resolved model, trust, reasoning selection, execution-agent binding, operations, and current directory. Each runtime owns its own database session. Child creation commits before scheduling, and cancellation joins startup work and child cleanup before deletion. The old internal Explore-run columns remain readable historical storage; new children do not use that loop or transcript format.

The task prompt supplies purpose and scope. Compatible project/profile guidance remains, but main-agent-specific Plan/Build workflow fragments do not turn the child into another main agent. Children do not copy the parent conversation and receive no automatic memory or prior-session retrieval. They use normal context budgeting and compaction, and inherit the parent's dirty active-file snapshot. Final result text is limited to 12,000 characters per child with an explicit truncation flag. Failed or budget-limited children additionally return a controlled cause and up to six recent useful tool results, each with at most 1,200 characters, its message/call references, error code, and bounded file actions. Synthetic budget, truncation, repeated-call, and skipped-after-denial results do not crowd out this evidence. These excerpts are untrusted data, not proof of task success; parents can read their own child sessions through the existing permission-controlled session tools. Children are excluded from ordinary chat lists, project counts, global search, episode indexing, and memory dreaming.

Delegation cannot widen authority. The child ceiling intersects the parent request's offered profile authority with live policy at spawning; execution then applies the stricter of that ceiling and live profile permissions, including integration/resource permissions and shell prefixes. It retains a concrete set of enabled integration UUIDs, so newly configured or newly enabled integrations cannot widen an existing child, even if the profile later changes. Technical availability, trust, owner/path/computer boundaries, and revocation remain live. The ceiling is applied to schema selection and handler policy reloads, not only approval requests. No credentials or integration configuration are copied into the ceiling. An instruction such as "do not edit files" narrows the task but is not a technical write sandbox. A Plan child retains Plan restrictions; a Build child retains the effective Build permissions. No child-type-specific tool allowlist exists.

Child approval and question records use the main session ID and the executing child run ID. Pending requests appear and are answered in the main session, with the child title and an inspection link. Only the child enters its waiting state. `allow_once` grants matching access for that executing child run; `allow_session` uses the main session's existing profile-, trust-, and resource-bound grant namespace without copying grants. Decision events are forwarded to the main run with child provenance. Pending-request APIs reconstruct the same attribution after reload. Skill drafts from children are previewed in their own root, read-only, and approval uses the exact initial draft revision.

Children share the selected computer workspace but retain their own managed session files, including within a project. The main agent must assign non-overlapping computer-workspace changes where possible and review the combined result. Existing revision checks, managed-file run ownership, and dirty-file guards remain effective. Neither separate sessions nor permission heuristics imply computer-workspace isolation. No automatic worktrees, rollback, or conflict retries are introduced. Completed mutations may remain after failure or cancellation.

Parent cancellation ends and joins all unfinished children and expires their live requests. Parent deletion and history removal clean dependent sessions and storage. Browser/SSE disconnect does not cancel work. Backend restart terminates interrupted runs without replaying tasks or effects. Completed child sessions remain inspectable until their owning history is removed. Independent child sends, retries, configuration, deletion, and session-bound file/terminal mutations are rejected with `session.readOnly`; owner reads and exports remain available. Read-only inspection does not make shared workspace bytes immutable to other authorized sessions.

The main activity panel shows clickable child titles and states. `/?session=<parent>&subagent=<child>` opens an independent read-only live inspector with breadcrumbs back to the main session, preserving the main draft, stream, and scroll container. It reuses existing message and activity presentation and adds only one selected-child stream alongside the main stream. Child text deltas stay in the child stream; the main stream receives compact lifecycle invalidations and actionable requests. Database state is canonical on load and reconnect. The inspector has no composer or independent run controls; questions and approvals link back to the main session.

PostgreSQL-backed lifecycle, parallelism, approval, cancellation, storage, and read-only tests run against temporary schemas with scripted providers, without external model calls:

```bash
./scripts/dev.sh test backend --subagent-db tests/test_native_subagent_integration.py tests/test_subagent_session_integration.py
```

## Tool Contract

A tool is a host capability with a stable name, description, typed input schema, and asynchronous execution. Providers receive only registry-exported schemas and return normalized tool calls. They never execute tools.

Research tools return structured results with safe URLs. `web_search` labels content as snippets; `webfetch` preserves safe final URL, content type, output format, final HTTP status, and retrieved content in a structured envelope. Transient context shortening preserves valid outer JSON and provenance URLs, but may explicitly shorten the inner content string even when it contains JSON, CSV, XML, or NDJSON. That string is not guaranteed to remain a complete or parseable document; the persisted result remains unchanged. Final-answer links are model-generated best effort; the host neither adds them nor treats them as proof. The frontend may show derived public metadata in a sources panel.

When a connected MatoLoop Agent offers `shell_run`, prefer it for direct API requests, custom HTTP, pagination, multiple requests, local processing, and downloads. Prefer `webfetch` for web pages and static documents; use an attached browser only for page interaction or browser-authenticated access. Supported structured MIME types are `application/json`, concrete `application/*+json` types, `text/csv`, `application/xml`, `text/xml`, `application/rss+xml`, `application/atom+xml`, `application/x-ndjson`, and `application/ndjson`. Their bodies are decoded verbatim into the existing `content` string, without parsing, reserialization, entity expansion, or additional resource requests. Default Markdown and explicit text return actual `outputFormat=text`; explicit HTML returns escaped `<pre>` content with `outputFormat=html`. No tools, providers, arguments, or permission exceptions are added. Source content remains untrusted, and existing network and response-size limits apply.

An unsupported MIME type returns the existing safe error with `statusCode` and a normalized, bounded MIME essence in `error.params.contentType`, without raw header parameters. A successful result with whitespace-only or empty content and no attachments adds `notice`: `No extractable text or attachments were returned. The cause is unknown.` The notice neither identifies a cause nor triggers automatic retry or browser fallback.

`session_tool_result_read` reads a persisted current-session tool result by message ID without executing the original tool again. The host returns fixed chunks of at most 12,000 characters from a zero-based offset and reports continuation through `hasMore` and `nextOffset`. Historical omission markers and shortened current-session tool messages returned by `session_read` contain a host-generated `toolResultReference` with exact retrieval arguments. Shortened tool messages from another approved session contain no unusable current-session reference.

Every eligible normal turn uses one bounded latest-message or short-follow-up query for automatic unpinned-memory and prior-session retrieval. The host shares one query embedding across both hybrid searches and falls back to FTS; durable-memory source provenance does not affect eligibility. Relevant and recent prior-session snippets come only from other owned `full` sessions across all projects and standalone sessions; a first turn or explicit recent-session overview can additionally use the recent-session quota. Project requests also receive a compact index of up to ten recent `full` sessions from the same project, ordered by each session's latest eligible message and containing only titles plus exact `sessionReadArguments`. They prioritize up to the configured maximum of distinct relevant owned sessions, default three, before non-overlapping recent snippets and unpinned memories. A relevant reference contains only the strongest topical anchor. Receiving `full` and `read_only` sessions may use these references, while `disabled` sessions receive none. An explicit opt-out or detected supplied-text transformation suppresses automatic context. References are untrusted discovery data, not complete transcript evidence. Explicit discovery and reading remain separate operations: `session_browse` lists recent prior sessions and `session_search` performs topic discovery across all owned projects and standalone sessions, both excluding the current session, and separately permission-controlled `session_read` supplies omitted details. These tools and authenticated UI search remain available for owned `read_only` and `disabled` source sessions even though automatic retrieval excludes them. Selecting the model releases already authorized session content; durable-memory audiences remain separately filtered. `session_read` can project a bounded window around `around_message_id` and continue forward with `nextAfterMessageId`. Models must not invent these IDs; within one run, a continuation must use the latest cursor returned for that target session. An unavailable or stale cursor fails closed with exact retry arguments. Its 50,000-character page budget advances only through messages actually returned, so continuation never skips an omitted record.

The tool registry is the only name resolver for tool calls. It rejects duplicate names during construction, validates input before execution, and exports only tools available for the session, effective policies, and effective integrations. Unknown tools, invalid arguments, and execution failures become stable tool errors. Exception text and secrets never enter model context or API responses.

Tool groups are host-controlled catalog and UI metadata. They do not grant access and have no policy inheritance. A tool declares zero or more security actions with stable capabilities, controlled UI labels, and explicit static private- and public-model policies. Built-in, integration, and resource permissions live on agent profiles; there is no global or personal policy baseline. The run's frozen trust level selects the profile's private or public map, and an absent entry falls back to the action's static policy. Tool settings contain only technical availability, Webfetch network parameters, and media timeouts. Instance-controlled availability and the Webfetch public-address restriction are independent hard caps.

Permission evaluation validates immutable host boundaries first. `disabled` then denies even when a matching grant exists, `auto` allows only inside those boundaries, and `ask` checks a matching run or session grant before creating an approval. After an approval, the host reloads policy and boundary state before allowing the effect. Groups are never permission matcher inputs.

Profile integration and resource permissions are keyed by the bound integration UUID, an adapter-generated stable resource key, and the action capability. For each trust level, the most specific present profile entry wins: resource, integration, then built-in capability, followed by the action's static policy. The permission request keeps this policy target separate from its typed grant matcher, so a calendar-level profile permission can govern an operation while a session grant remains limited to one concrete event.

Integration settings own technical connection configuration and host-selected search providers. `GET` and `PUT /integrations/{integration_id}/access` support only CalDAV and expose only its standard calendar and task-list resources; they do not edit permissions. Profile permissions use `disabled`, `ask`, or `auto`, and invalid persisted modes fail closed. Technical tool availability, disabled integrations, remote service ACLs, trust, ownership, path, computer, and delegation ceilings are hard limits that no profile, approval, or grant can raise.

Profile integration availability is a separate, trust-independent selection layer: `integrationsEnabledByDefault` supplies the default, and `integrationAvailability` maps canonical integration UUIDs to strict booleans. An absent entry inherits, `true` opts in, and `false` opts out; inheritance is omission, not a stored `null`. In the editor, "Integrationen standardmäßig aktivieren" controls the default, with "Standard (Aktiv)" or "Standard (Deaktiviert)", "Aktiv", and "Deaktiviert" per instance. Changing the default preserves explicit entries. Selection never grants an action or changes an integration's technical enabled state. Private/public integration and per-resource permissions reuse the existing sparse maps and typed grant namespace; there is no second resource permission system.

The selection filters a runtime copy before contributions, shared-account enumeration, option binding, schema export, and execution. It includes option-only and project integrations, not just integrations with configurable actions: OpenCode project coding, OpenSCAD, and SearXNG all obey it. Excluding the configured primary SearXNG instance makes `web_search` unavailable rather than silently switching to `no_key`; an excluded fallback is removed. Explicitly selected `no_key` remains independent of integrations. Scope validation permits only configured instance/personal IDs in the profile's allowed scope; unchanged stale entries can be preserved or removed, but not newly assigned or changed to bypass that scope.

Integration selection, binding revisions, and applicable resource policy are reloaded before effects and after approval, including nested directory approvals and aggregate resource handlers. Approval cannot revive a revoked integration or resource. Children intersect this live state with their concrete delegation ceiling, and aggregate handlers retain scoped resource keys while reevaluating their policies rather than restoring stale permission values.

Configured integrations resolve through a static host catalog. An adapter can contribute statically implemented tools or values to a configuration field declared extensible by a base tool. Such values do not automatically become model arguments. Adapters cannot load foreign handlers or arbitrary remote schemas. Prompt fragments come only from adapter code; names, responses, and other external data are never treated as instructions.

A contributed tool with configurable actions must provide a host-side authorization factory. The registry validates every produced permission request against the actions declared by that tool before its handler runs. Integration settings cannot declare capabilities or authorization behavior.

For a selected integration resource, the registry refreshes effective policy and technical availability before performing a host-only metadata preflight. Missing resources, inapplicable actions, and remote ACL denials stop the call before creating an approval. Discovery may use authenticated, read-only resource metadata requests, but does not fetch resource content or release discovered metadata to the model. Integration bindings and resource restrictions are checked again after authorization before content access or mutation.

The effective tool set is bound for exactly one model request. Schema export, option validation, and subsequent execution use the same binding. Calls outside this set are rejected even when a global tool definition with that name exists. Before external effects, handlers reload revocable integration, tool, and capability configuration.

Bindings retain their source integration ID and a canonical revision of that integration instance. Deletion, disabling, credential replacement, or configuration changes invalidate an already offered contributed tool. Host-selected provider options are bound to the same request; execution never silently switches a stale call to a different provider.

Every execution receives host context containing at least run ID, current session ID, registry-independent services, and `Context.ask`. Tools do not access coordinator waiters, approval tables, or provider objects directly. `Context.ask` accepts a typed permission request and centrally performs this sequence:

1. Check immutable host policy.
2. Check a matching persistent session grant or a grant bound to the current run.
3. If still needed, create a persistent approval and wait on the process-local coordinator.
4. Return typed `allow_once`, `allow_session`, or `deny`.
5. For `allow_once` or `allow_session` and a live run, persist the run-bound or session-bound grant in the approval transaction, then resume the waiter. Argument edits create their exact run grant only after the final arguments have been revalidated.

Model arguments cannot bypass registry selection, `Context.ask`, capability boundaries, or resource matchers. Tool content access and mutations occur only after an allowing result; the host-only resource metadata preflight above is part of authorization. Copy and move stop after a denied source permission without asking for a destination permission that cannot make the operation succeed.

This permission sequence also governs `shell_run` in the attached shared Bash terminal, including ordinary class-specific prefixes and session grants. There is no terminal Auto/Confirm mode or policy replacement. The proposed model command is immutable and a pending call has one persistent approval, reviewed read-only in chat or **Benachrichtigungen**. Session, run, owner, agent, workspace binding, actual terminal cwd, and inspection revision are revalidated before execution. Denial discards the prepared command; cancellation during execution interrupts the foreground process, while the stop control in chat cancels the run. Browser input remains disabled for the complete agent-controlled turn.

Agent profiles are persistent instance- or user-scoped settings. Every session stores a profile ID; the independent core profiles `Allgemein`, `Plan`, `Build`, and `Sysadmin` cannot be renamed or deleted, and `Allgemein` is selected for new sessions. A resolved profile owns its persona selection, task and runtime instructions, model fields, integration availability, shell prefixes, and trust-scoped capability, integration, and resource permissions. Tool-independent profile permissions appear as group actions in the same catalog as tool actions. `working_directory.external` is such a group action and controls model file and inspected shell targets outside the selected working directory independently of their action policy. It defaults to `ask`; Plan and Build keep `ask`, while Sysadmin uses `auto`. `Plan` permits `filesystem.read` and `shell.read` but disables direct computer mutations, managed session-file writes, and known `shell.write` actions. `Build` permits computer reads, writes, deletions, and shell actions. `Sysadmin` permits computer reads automatically and requires approval for filesystem writes, deletions, and known shell mutations. These policies apply to both trust levels and may send read results to public model providers without individual approval. Incomplete shell inspections without a recognized mutation remain `shell.read`, including in Plan and Sysadmin; classification is not a read-only sandbox. The runtime snapshots the selected profile ID on each run and applies it consistently to model selection, schema binding, and authorization. Instance administrators may disable personal profiles. Session grants created from `ask` bind to the selected profile and frozen trust level, so neither switching profiles nor switching between private and public models reuses the grant. Filesystem `deny`, shell-zone switches, technical availability, disabled integrations, confidential-path restrictions, ownership, remote resource ACLs, and delegation ceilings remain hard boundaries for every profile.

Profiles also control the session checklist tool. It defaults on for `Plan`, `Build`, and `Sysadmin`, and off for `Allgemein` and new custom profiles. When available, the model uses it only when a checklist materially helps the task or the user requests one; no fixed step or tool-call count requires a checklist. Each successful `todo_write` result is a complete replacement snapshot. Session details expose the latest successful state. Model context instead seeds a stable checkpoint before the latest request, reconstructed through the compaction boundary when necessary; later successful tool results replace it in chronological order. Current checklist results are not shortened. Capability changes do not erase recorded state. This message-backed state needs no separate table and naturally follows history deletion, undo, and retry. It records reported progress only and never authorizes or verifies an action.

The checklist is docked above the composer, including while a question replaces the input. It starts expanded. The session API exposes `todosCollapsed` and accepts the independent `todos_collapsed` patch field, stored in the existing `control_center` JSONB document; layout updates preserve it. A missing key means expanded. This preference is separate from runtime policy and can change during a run. Session details and live run transitions hide a completed/cancelled-only snapshot when a later top-level run exists, until a new snapshot is written. Pending or in-progress items carry over. This display rule does not delete history or change the model-context checkpoint. Session details include `latestRunId` so reconnecting to the same run does not hide its newly completed checklist.

### Profile Inheritance

`Allgemein`, `Plan`, `Build`, and `Sysadmin` have code-owned workflow definitions and stable IDs; administrators configure sparse access and model overrides for each independently, but cannot rename or delete them. Integration adapters may contribute additional protected profiles; duplicate shipped IDs fail registry validation. Instance settings contain those built-in overrides and custom profiles; personal settings contain custom profiles only. Every custom profile selects exactly one core base and cannot inherit from another custom profile. Runtime and API consumers receive a fully resolved profile plus base and sparse-override metadata. Model catalog changes remove invalid profile model fields; integration binding changes and deletion remove stale profile integration/resource permission references.

### Profile Model Resolution

An explicit session model wins, followed by the resolved profile's `defaultModelId`; no global or personal AI default participates. An explicit session reasoning effort wins over the profile value, after which the provider's model default applies. Session-bound compaction, title, skill-builder, vision, video, media, and transcription requests use the same resolved profile fields and their documented active-model fallbacks. Profile-independent manual and scheduled Dreaming resolve `Allgemein`, so they do not depend on a source session profile.

`delegationEnabled` and `sessionWritePaths` are inherited effective fields. Allgemein and Sysadmin use `false` and `null`, Plan uses `true` and `[]`, and Build uses `true` and `null`. Null adds no profile restriction and `[]` denies all managed session writes. Non-null entries must be normalized relative POSIX file paths. Permission evaluation, approval rechecks, and delegation snapshots enforce the effective restriction; a delegated run can never widen it.

## Typed Resource Matchers

A permission consists of a capability and typed resource matcher. Security decisions never depend on free-form display strings, string-prefix comparisons, or tool names. Matchers have unique types and validated fields such as canonical path, session ID, defined session-search scope, or shell token sequence.

- Path matchers contain explicit `session` or `workspace` root and compare relative paths component by component inside the host-bound root; string-prefix matching is forbidden.
- Computer area matchers use canonical `{agentId,path}` JSON and compare normalized absolute POSIX paths component by component. `resource.read` and `resource.write` grants cover matching file-tool and inspected shell targets; string-prefix matching is forbidden.
- Explicit authenticated computer/directory selection creates the same profile- and trust-bound directory grant for permitted `auto` and `ask` zones. The grant permits directory use within the selected subtree, not file or shell operations. Denied zones and missing bindings create no grant. Existing sessions can explicitly reselect their directory; grants are not backfilled on startup or recreated by normal runs after revocation.
- Session matchers compare UUIDs and distinguish the current session from an explicitly named other session.
- Project-session file grants match the exact canonical project ID, target session ID, and relative path. Repeated reads and pagination reuse them under `ask`; each evaluation rechecks current ownership, project membership, and target-session eligibility. They do not authorize another path or a subtree.
- Personal-profile update grants bind the owner and resolved data audience (`private_models`, `public_models`, or `both_models`) in addition to the normal session, agent-profile, and executing-model trust binding. They cover profile updates for that audience, not only the fields displayed in the first request. Legacy owner-only UUID grants do not authorize a new audience-bound request.
- Session-search matchers represent browse and search as one collection resource. A grant to read one session does not allow either discovery operation.
- URL matchers use the SHA-256 hash of the complete canonical URL. Display metadata separately persists that complete canonical URL, including query values.
- Persisted matchers deserialize losslessly to the same typed matcher.
- Approval display title, summary, and risk are metadata, not matching inputs.
- Integration session grants compare the integration UUID, canonical binding-revision hash, and host-generated stable resource key. Operation keys and arguments remain one-time approval inputs and are never reusable grant identity; remote labels and URLs are display-only.
- Mail grants are account-bound because that integration exposes account-level policy. Plaintext message locators and ciphertext tokens are not stored in the grant matcher.
- Shell requests retain the host-generated `shell.read` or `shell.write` classification. Class-specific token-prefix allowlists remain policy inputs, while session grants compare every recognized ordinary path against same-class computer-area grants. Disabled capabilities, hard shell-zone switches, filesystem `deny`, confidential paths, and inspection revisions are evaluated before grants.
- Image-edit matchers retain direct attachment provenance separately from a bounded host-controlled authorization lineage. Descendants inherit lineage roots; unrelated images, sessions, targets, and trust levels do not match.

Selecting a model is the release decision for integration data already authorized by ownership, integration access, tool policy, and approvals. Public models do not require a second session-wide private-data release.

For Shared File Tools, the model uses `root=files` for the backend-managed revisioned root and `root=computer` for the current absolute directory on the selected owner-bound MatoLoop Agent. The registry translates these to internal `session` and `workspace` identifiers before permission checks. Model paths never start with a root-name prefix; the standalone `filesystem.*` request receives a normalized absolute POSIX path. Every session uses its session UUID as managed-file root identity. Explicit access to another session requires the same owner and current project membership. Computer access is unavailable without an agent and selected directory, while managed files remain available. MatoLoop Agent filesystem traversal uses descriptors and no-follow checks on every path component.

Standalone physical storage is `/data/sessions/<session-id>/{files,revisions}`. Project-session storage is `/data/projects/<project-id>/sessions/<session-id>/{files,revisions}`. Uploads, processing companions, and durable backend artifacts all use the owning session's managed revision store.

Published backend-managed files have full-byte revisions. During a run, creates, copies, replacements, and durable tool outputs write the normal current file, not a private copy or numbered intermediate revision. Tools and users read the same live bytes. A run owner stored in the existing revision index blocks competing file and subtree mutations; unrelated files remain independently editable. Completion, failure, cancellation, and restart recovery snapshot one final revision per changed file; unchanged final bytes create no revision. Existing files retain their original snapshot before the first run edit. Publication is idempotent and per-file, using index receipts rather than a separate byte journal. Directory creation and permitted rename/move are immediate and preserve file identity. Current bytes and retained revisions share the root quota, with space reserved for final snapshots. Browser/API replacements retain expected-SHA conflict protection.

Deleting a managed file purges its complete history and explicitly owned derived files; ownership is never inferred from similar filenames or paths. Individual revisions cannot be deleted. Activating a retained revision changes only the selected managed file's live bytes and current-revision pointer without creating or removing a revision. Separate managed companions, their histories, and ownership metadata remain unchanged. Competing mutations of run-owned files are rejected; activation waits for finalization even for the owning run. Old message references survive edits, moves, and revision activation; deleting the complete file makes them unavailable.

Historical file access is an authenticated user feature, not a model tool. The viewer opens retained versions in separate read-only tabs keyed by root, file identity, and revision, independently of the current file. Safe standalone formats use their historical bytes; dependency-based OpenSCAD history shows source only, without rendering against current dependencies or substituting current geometry. Models read only live current file content; attachment and provider reads reject superseded references rather than loading old bytes.

Managed reads use `session.files.read`; writes, edits, directory creation, copy destinations, and both sides of a managed move use `session.files.write`. Both capabilities default to `auto` for private and public models. Saved policies and profile overrides remain effective; an explicit `filesystem.read` rule also governs managed reads until a `session.files.read` rule replaces it at that scope. Workspace policies and Plan-profile path restrictions are unchanged.

Managed deletion uses `filesystem.delete` with `ask` for both private and public models, even if a configured policy is `auto`; disabled policies and host boundaries still deny. The ordinary typed grant and approval loop applies, including matching session grants, rather than unconditional repeated confirmation. Direct owner-authenticated UI deletion remains a separate user action.

Each `ExecutionAgent` has home and external filesystem policies with `auto`, `ask`, or `deny`, defaulting to `auto` and `ask`. They govern explicit directory selection, and `deny` remains a hard model boundary; the active profile's `working_directory.external` policy controls ordinary model access beyond the selected working directory. Hard boolean shell switches control the home and external zones, and both default to enabled. Every zone identified by shell inspection must be enabled; incomplete analysis also requires the external shell switch and cannot bypass external filesystem `deny`. A recognized direct or nested mutation makes the command `shell.write`; otherwise it is `shell.read`, even with incomplete analysis. `readOnly` is only the legacy protocol alias for that class. Unknown program effects and incomplete analysis are an accepted workflow risk, not an unresolved sandbox requirement. Shell permissions and token-prefix allowlists come from the selected profile; the execution agent's hard filesystem and shell-zone boundaries remain effective.

Syntax errors return controlled `process.invalidSyntax` before execution, not a write approval. POSIX `<>` is supported as a non-exempt write redirection. Command-text, enumeration, and target-count bounds return `process.inspectionLimitExceeded`. Serialization caps on command nodes or tokens remove reusable prefixes and mark extraction incomplete, but never stop inspection of later known writes or hard paths. Missing required literal targets retain their absolute paths and mark analysis incomplete; hard no-follow and access errors remain failures rather than missing-target uncertainty. Isolated execution and shared Bash use the same inspector and revalidate the exact inspection revision before execution. Shared-shell state adds no forced-write classification: commands without a recognized mutation remain `shell.read`, including incomplete analysis.

Redirect targets are read from their first AST destination; trailing command arguments remain part of command and path analysis. ANSI-C-quoted path targets are rejected with `process.unsupportedTargetQuoting` instead of fabricating a literal path through shell-independent quote stripping. Use ordinary literal path quoting. Non-path ANSI-C strings leave extraction incomplete and suppress reusable prefixes; no general ANSI-C decoder or second shell parser is introduced.

Shell-only `discard` and `toolchain_metadata` targets skip only soft outside-current-directory approval, not ownership, filesystem `deny`, shell-zone switches, confidential-path checks, effective shell policy, or revision validation. `discard` requires a static output destination of exactly the real `/dev/null` character device `1:3`, verified without following symlinks; input use and `<>` are not exempt. Toolchain metadata is limited to simple installed `ls`, restricted options, and flat directory or basename/glob discovery in the six actual execution `PATH` directories, with bounded listing fingerprints. No recursive/dereferencing option, wrapper, or arbitrary directory-symlink exception is added. Verified standard usr-merge aliases are narrowly supported; hidden entries, external file-link destinations, and dot globs covering `.` or `..` retain ordinary targets, and `/usr` is not exempt. An ordinary content use of the same path overrides its special kind. The exact discovery scope is documented in [MatoLoop Agent Boundary](architecture.md#matoloop-agent-boundary).

The shell inspector remains coordinated between backend and agent under protocol v1. The resource-grant data migration removes approval-created legacy action and shell-prefix grants instead of widening them. Older agents remain conservative; the backend never converts their write classifications to read. Historical approval display text is unchanged.

Managed-file mutations continue to use `session.files.write`. Requested saved artifacts use one ordinary `root=files` file per artifact unless the user requests `root=computer`; edits read and update the same path. Otherwise, generic writing may be answered inline unless a workflow requires a saved artifact. Messages may carry a metadata-only active-file snapshot, and matching writes are rejected while it is dirty.

`shell_run` accepts optional `timeout` in seconds with `0 < timeout <= 3600`; omission or `null` uses the MatoLoop Agent's `defaultTimeoutSeconds` (60 by default). Isolated and shared-shell execution use the minimum of that requested/default value and local `maxTimeoutSeconds` (3600 by default). Nonzero exits and timeouts become controlled `process.commandFailed` or `process.timedOut` tool errors while retaining bounded stdout/stderr or merged PTY output, exit code, and truncation metadata. Shared results retain requested and executed arguments and whether the user edited them. Uncertain completion becomes `process.outcomeUnknown` and is never automatically replayed. The model must interpret output in context rather than equating every nonzero exit with the same failure.

Without terminal attachment, `shell_run` starts an isolated shell in the selected session directory, so `cd` and shell-state changes apply only to that call. With attachment, it uses the same live Bash PTY as the user: `cd`, environment, variables, aliases, and functions persist across calls. This does not change the chat workspace; `change_directory` remains the tool for changing the session/run directory used by file tools and other computer operations. Run instructions must distinguish these two execution paths rather than treating every shell `cd` as call-local. The personal shell remains usable between agent commands without detaching. Browser reload and session switching do not end it, but backend or agent restart does; lifecycle and native pending-edit restrictions are described in [MatoLoop Agent Boundary](architecture.md#matoloop-agent-boundary).

Process startup keeps the actual working directory descriptor-bound: subprocess startup uses the opened directory through procfs, and PTYs use `fchdir`. Logical `PWD` and `HOME` contain the canonical current-directory path for one-shot commands, never `/proc/self/fd/...`; the detached user terminal starts with the agent home path. Executables use validated canonical paths so shebang scripts retain their usable path and `$0`. Validation and path-based execution are not atomic and do not provide descriptor-bound executable identity or a secure exec sandbox. This retains the documented non-sandbox tradeoff; it does not weaken the descriptor-bound working-directory contract.

Plan and Build prompts are task-general. Plan matches investigation depth to the requested deliverable: questions and idea assessments receive a concise assessment, while explicit planning requests receive an actionable plan. It stops when sufficient evidence is available and does not substitute a simpler but different feature. Build uses that conversation context when the user later requests implementation, applies newer instructions over the plan, carries out the work, and verifies the result. Context compaction preserves the current plan, user corrections, open decisions, and remaining steps while distinguishing planned work from verified work. Applicable `AGENTS.md` instructions are required for repository work before edits, not for unrelated tasks, and remain below host rules and the latest user request. Delegated tasks specify the exact question, scope, stopping condition, and result format/length; children return the assigned findings rather than expanding them into full plans. This is generation guidance, not a new runtime word or tool-call limit. Delegated tasks retain inherited permissions without being forced through the main Plan/Build workflow.

The Plan prompt forbids intentional changes to computer files, system state, or external services and forbids using shell commands to bypass disabled write tools. Those instructions and the direct-write restrictions do not guarantee side-effect-free planning: unknown shell effects may still be classified as `shell.read`.

For `webfetch`, the effective `network.fetch` policy is evaluated for every initial URL and redirect. `ask` requests approval for the exact URL, while `auto` permits the request without approval. The target is resolved again after approval, and the validated addresses are pinned for the request. Tool availability and the instance-wide public-address restriction remain hard bounds. The restriction blocks every non-public address by default; disabling it deliberately permits every HTTP(S) target reachable from the backend.

User uploads and processing companions use revisioned managed files. Run output descriptors remain private JSON under `Message.provider_data._matoloop` until terminal finalization; pending attachments are not public `MessageAttachment` rows, and pending file actions are omitted from API responses. Finalization publishes deduplicated final attachment references with exact root, file ID, revision, and path snapshot; publication failures leave pending output metadata private. File-operation receipts retain confirmed actions, including deletions, and appear in a compact per-response change list. `provide_file` publishes a reference to the original session file or computer path, not an imported attachment. Session references retain the final available revision as a separate historical target. File references and ZIP selections load only on explicit open or download; generated media retain their ordinary inline previews. Terminal events refresh already open files but do not automatically open output tabs. Text, JSON, status, and error results remain relational `Message.content`.

OpenSCAD OFF geometry and inspection PNGs/contact sheets are ephemeral preview data consumed inline, not public file artifacts or numbered revisions. Persisted tool results retain diagnostics, geometry metadata, and visual-verification findings without preview-file references. Explicit STL exports remain durable managed outputs under the same terminal publication contract.

The binding baseline for session tools is:

| Action | Resource | Result without grant |
| --- | --- | --- |
| Read session history | owned eligible session | effective `session.read` policy |
| Read persisted tool result | current run session | effective `session.tool_result.read` policy |
| Browse or search sessions | session-search resource | effective `session.search` policy |

`session_tool_result_read` accepts only tool messages from the same session. Browse and search share one collection grant; reading a discovered session still requires its separate exact session grant. A suitable session grant can allow a later identical request but never expands matcher type or scope. These unconfigured session-history read capabilities default to `auto` for private models and `ask` for public models.

## History and Request Context

Canonical history is the persistent normalized sequence of session messages, including assistant tool calls and results. It remains complete and available in stable order. Provider payloads may be persisted additionally but never replace normalized history.

Request context is a transient projection for one model request. It can contain system instructions, every visible pin in full, bounded automatic snippets from relevant unpinned memories and prior sessions, explicitly retrieved details, a compaction summary, and a budgeted slice of canonical current-session history. Automatic snippets share a separate serialized budget and can be dropped to fit; pins cannot be truncated or dropped, so projection fails safely when they cannot fit with required context. Shortening, reordering, and provider conversion never modify or delete canonical messages.

When context omits a historical tool result, it inserts a structured reference to the canonical message ID. The model reads required details through `session_tool_result_read` instead of rerunning the tool. Raw output from that read is not duplicated in compaction summaries.

Tool call and result are indivisible when slicing context. A request cannot begin with an orphaned tool result or call without result unless it is the active call awaiting execution. The latest user request remains in context.

## Compaction

Compaction creates a persistent marked summary of a completed canonical-history prefix. The summary has an unambiguous coverage boundary so the request builder selects exactly that summary and messages after it. It never replaces, edits, or deletes covered messages.

A summary preserves goals, relevant facts, decisions, and open items from user and assistant chat text plus bounded operational tool evidence. The host extracts only allowlisted short scalar and nested result metadata, such as status, exit codes, counts, numeric values, paths, revisions, and errors, alongside exact message IDs, tool names, call IDs, and `toolResultReference` retrieval arguments. Raw stdout/stderr, arbitrary tool-result prose, call arguments, attachments, and approval records are not wholesale summary input. The evidence block is explicitly untrusted; a successful call does not prove task success, and omitted results must not be inferred.

The summarizer receives up to 6,000 characters of recent serialized evidence entries. The host appends a deterministic evidence block to each persisted summary with up to 2,000 characters of entries, plus fixed trust and coverage markers and an exact `session_read` anchor for earlier evidence. Canonical tool results remain unchanged behind `session_tool_result_read`; the retrieved raw content is not copied wholesale into the next summary. A structurally invalid or empty model result is rejected; if no configured model produces a valid summary, the host persists a marked deterministic fallback and the transcript displays a warning.

The same summarization request also receives up to 6,000 characters of already-authorized user and assistant chat excerpts from successful `session_read` results in the covered prefix, plus a fixed untrusted-data header. Recent reads take priority; source session/message IDs deduplicate excerpts within that request, including chat text already supplied directly. Excerpts retain source IDs, roles, timestamps, and interruption or truncation flags. Long text retains its beginning and end with an explicit omission marker. Nested tool bodies, reasoning, attachments, and call arguments are excluded, and references never trigger automatic reads. The summarizer must retain relevant facts, decisions, and open items with attribution rather than only their retrieval references. The existing summary output target, provider protections, preflight, and fallback remain unchanged; references still allow targeted retrieval of omitted details.

Compaction triggers from estimated input budget, not message count, and can advance within one long user turn. Boundaries never split assistant-call/result batches or cover a pending or partially completed parallel batch. The latest user request and at least the last two complete current-turn batches remain in the active projection, along with pending calls. If the coverage boundary passes the user message, it is reattached only as a projection anchor, not added back to the uncompacted history or repeatedly summarized after reload. Repeated compaction must not reinsert already compacted prefixes without bounds. The implementation deterministically chooses the active summary among generations.

## Model Context Settings

`contextWindowTokens` is the configured context capacity, with a configuration minimum of two tokens; this does not guarantee enough room for a runtime request. `maxOutputTokens: null` selects Auto, the default for new manual and discovered models. A strict positive integer selects a manual output ceiling, not a fixed output reservation. The stored ceiling is neither clamped to a quarter of the context window nor rewritten when the context window changes. Effective allocation may be lower without changing the saved value.

New discovered models automatically use the endpoint's reported context capacity. Codex supplies an allowed maximum (`max_context_window`) separately from its default (`context_window`); discovery prefers the maximum when present. A local server's configured context, such as Lemonade's `context_length` or `ctx_size`, takes precedence over its theoretical maximum. Explicit manual context overrides remain independent. After an adapter update, synchronize the provider to refresh existing provider-following models; deployment alone does not change stored limits. There is no global 128k or 272k context ceiling.

`discoveredMaxOutputTokens` is a read-only nullable provider ceiling. Only the documented OpenRouter `top_provider.max_completion_tokens` field currently supplies an authoritative value; absent, invalid, or ambiguous metadata leaves it unknown (`null`). Generation defaults, model names, and context capacity are not evidence of an output ceiling. Synchronization refreshes this field for matching manually entered models as well as discovered models, including clearing it when the returned metadata no longer supplies a valid cap. Manual output settings and existing context-window source selection remain independent.

For an ordinary agent request, let `C` be context capacity, `S` the fixed safety reserve (4,096 tokens by default), `M` an optional manual ceiling, and `H` an optional known provider ceiling. Omit absent limits from each minimum:

```text
R = min(2048, M, H)
capacity = max(0, C - S - R)
input_budget = raw_input_budget(capacity) = capacity * 10 // 11
trigger_budget = min(input_budget,
    raw_input_budget(max(0, floor(C * compaction_trigger_ratio) - S - R)))
```

`R` reserves a useful generation turn; it is not the output ceiling. System instructions, tool schemas, memories, summaries, history, and projected image estimates count against this raw input budget. ContextManager uses the same inverse-margin calculation for its compaction trigger and transient tool-output budget. Automatic memory snippets use at most 10% of the raw input budget under their separate configured cap. The inverse factor is `10 / 11`, not a subtraction of 10% from capacity: it leaves room for a later 10% increase of the raw estimate. Projection estimates include neither that increase nor the fixed safety reserve.

ContextManager uses `ProviderService.prepare_request` through an async estimator for every whole-request fit decision, including after compaction and tool-output shortening. This is the same local media projection, pseudonymization, tool-schema conversion, continuation selection, and serialization used by completion. For the compaction decision, the existing zero-budget shortener is applied in a copied candidate only to tool bodies after the compaction boundary; older tool bodies remain counted. Compaction occurs only when that request still exceeds the trigger. A separate candidate shortens every current tool body to determine their final shared budget. Both retain unavoidable markers, short results, and privacy overhead. Run-bound attachment filtering occurs before image deduplication and estimation. Preparation does not load credentials/settings or call authentication or model endpoints, and always starts from original, unprotected messages.

After shared preparation, ProviderService allocates output:

```text
I = max(raw_projection_estimate, raw_final_serialized_estimate)
guardedI = ceil(I * 1.1) = (I * 11 + 9) // 10
output = min(C - S - guardedI, M, H, Q)
```

An absent projection estimate contributes zero. `Q` is an optional explicit per-request helper ceiling, not another persisted model setting. The proportional margin is applied exactly once, after taking the maximum of the two raw estimates. The fixed `S` is also subtracted once. The default service-level generation reserve is `min(2048, M, H, Q)`; the normal agent passes its projection's `R`, and a helper may explicitly reserve its full bounded output. An allocation that is nonpositive or smaller than the required reserve fails with `agent.contextWindowExceeded` before credential loading or transport. ContextManager reports `agent.contextWindowTooSmall` when no raw input budget exists, or `agent.contextWindowExceeded` when required context still cannot fit after compaction and shortening. Unchanged inputs produce matching projection and final estimates; final revalidation still protects against changes such as attachment availability between passes. ProviderService does not recursively invoke compaction. When `M`, `H`, and `Q` are all absent, the allocation remains a local fit allowance and compatible transports omit the output-limit field so the provider can apply its own default. A present cap is reduced by the available context before transmission.

Input estimation uses serialized input framing, instructions, messages, tools, and continuation with the model's characters-per-token ratio. It excludes generation options and transport metadata and does not count binary/base64 payloads as text. Each image adds a 2,048-token input estimate; audio, video, and unknown opaque continuation each add an 8,192-token heuristic reserve. Scope-matching Responses reasoning uses the originating response's reported reasoning tokens plus 256 tokens for opaque framing, shared across its replay items with upward rounding. This requires nonnegative integer usage not exceeding the response's reported output tokens; otherwise the fixed fallback applies. The active reasoning chain is not pruned, and estimates never enter the wire payload. These are not tokenizer measurements or upper-bound guarantees. Long media, large inputs, unknown server templates, or different tokenization can still require a lower manual output ceiling or produce a provider context error. There is no hidden 2,048-token output cap for requests containing media.

Helpers keep their own small explicit ceilings rather than taking all Auto headroom. Titles start at 2,048 tokens and allow one repair up to 4,096, subject to manual and known provider ceilings. Compaction requests have a bounded summary target of 256 to 2,048 tokens, capped by the helper model's limits, reserve that effective output in full, and use the same prepared-request allocation as other completions. Compaction's model attempts and transport retries share a 20-second overall deadline, shortened by a lower configured request timeout; expiry cancels provider work and uses the marked deterministic fallback. Other explicit helper caps remain in force. The `/models/{model_id}/test` connection test supplies an explicit 1,024-token helper ceiling, subject to the transport behavior described below.

Adaptive allocation is provider-neutral and has no Qwen-specific branch. All existing reasoning defaults, effort selection, supported disable rules, summary visibility, and continuation rules remain unchanged for every model. Auto output does not introduce automatic thinking selection or enable reasoning.

For Chat Completions, `halogen-qwen3.8-flash-next` exposes the Halogen 0.11.10 reasoning levels `none`, `minimal`, `low`, `medium`, `high`, and `xhigh` in the existing session selector. The default remains `xhigh`; discovery-provided reasoning profiles take precedence. Halogen maps minimal/low to low and high/xhigh to xhigh. Enabled levels use `reasoning_effort`; disabling uses `chat_template_kwargs.enable_thinking=false`. Selecting an effort does not change sampling parameters or add a thinking-token budget.

ProviderService returns host diagnostics in `provider_data["output_budget"]`, separately from actual provider usage. Normal assistant persistence carries these into `_matoloop.performance`: raw and final input estimates, guarded input, safety and output reserves, manual/provider/helper limits, mode, estimation policy, and computed versus transmitted output. `allocatedOutputTokens` is the effective computed allowance; `transmittedMaxOutputTokens` is the actual request option. Compatible Chat Completions sends `max_tokens`, and compatible Responses sends `max_output_tokens`, only when a manual, discovered, or helper cap exists. With no known cap they omit the field and use the provider default. Codex always omits generation options. An omitted option records `None` (`null` in JSON) even though a host allowance is computed; diagnostics must not imply that the provider received or enforces that allowance. No transport's estimate is a guarantee of actual token use.

### One-Time Auto Migration

Data-only Alembic revision `49e718887770` switches every existing model in all instance- and user-scoped `ai` settings documents to Auto, including models with explicitly chosen manual output limits. It handles top-level and legacy nested output fields without a relational schema change. Applying this migration deliberately destroys the old output ceilings: no backup is kept. Downgrade removes output settings, including manual ceilings entered after the upgrade, so older code uses compatibility defaults; it does not restore historical limits. New manual ceilings entered after upgrade remain in force during normal use and synchronization.

The migration preserves context settings, user-selected reasoning, temperature, and all other configuration. It does not rewrite old runs or canonical history. This contract describes implementation and upgrade behavior, not a unit-test or live-provider validation result; validation reports are maintained separately.

| `CONTEXT-03` | Same current tool output projected for different model windows | Requests build | Tool budget scales to model-dependent compaction threshold; canonical tool message is unchanged. |

The restart boundary is tested independently in `apps/backend/tests/test_harness_restart_contract.py`. Registry, session tools, matchers, compaction, and model context settings receive executable tests when their public contracts exist.

## Coding comparison reports

`./scripts/eval.sh coding-comparison` compares existing MatoLoop harness metadata with an OpenCode session export and writes a versioned JSON report plus Markdown. The JSON retains source paths and SHA-256 hashes, run identity, available objective metrics, and deltas only where both artifacts expose the same metric. It declares quality unknown unless both artifacts contain independent `checks`; it never treats duration, token use, approvals, or model self-reports as proof of correctness. Raw reports under ignored `data/` are local evidence and should be summarized in tracked documentation when they support a lasting decision.
