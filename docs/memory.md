# Memory and Dreaming

## Trust Model

MatoLoop distinguishes `public` and `private`. Every provider has a required trust level. Models can override it in either direction or inherit it with `null`. At the start of an agent run, the model ID, effective trust level, and effective pseudonymization setting are persisted. Changes to model selection or policy during an active run therefore apply only to the next run. Every generated user, assistant, and tool message carries the trust level of its run. A session is permanently tightened to `private` once a private run participates; this is a conservative history indicator, not the release decision for the next model request.

Memory access follows the trust snapshot of the active run: public models read only public memories and write public memories; private models read both levels and write private memories. Persisted private `memory_retrieve` results are redacted before a public model sees them. Public `session_read` and `session_search` calls return only messages with public provenance regardless of approval; `session_tool_result_read` likewise accepts only public tool messages. Normal user and assistant messages in the current history are not removed by trust level.

Effectively public models locally protect validated identifiers and recognizable secrets in released text by default. Independent Presidio recognizers cover email addresses, IP addresses, phone numbers, IBANs, and credit-card numbers; `detect-secrets` adds structured keys, tokens, secret assignments, and private keys. People, places, and other free-form entities are not detected. The transient request-scoped mapping also restores response deltas and tool arguments; unknown markers from the current request cause a controlled error, and opaque continuation state is dropped. Providers and models can explicitly disable this protection. In that case the public provider receives the released context unchanged. Images and binary file data are not pseudonymized separately. Detection is best effort, not a complete confidentiality boundary. Trust level controls model data release; it does not encrypt the database.

## Session Memory Mode

Every session has a mutable `memoryMode`. `full` enables active memory, `memory_retrieve`, `memory_write`, and dreaming. `read_only` enables active memory and `memory_retrieve`, but not `memory_write` or dreaming. `disabled` disables all memory access and dreaming. New sessions start with `full`.

The mode is current session state. Switching back to `full` allows dreaming to process all messages not yet covered. The mode does not affect chat persistence or `session_read`, `session_tool_result_read`, and `session_search`. User-scoped memory settings and provider or model policies can further restrict effective capabilities. Agent runs require tool-capable chat models, so both automatic context and `memory_retrieve` are available whenever read access is enabled.

## User-Scoped Settings

`MemorySettings` is entirely user-scoped. It contains the general memory switch, automatic dreaming switch, active-memory character budget, lifecycle thresholds, additional dreaming instructions, intervals, and batch limits. Defaults are 20,000 active-memory characters, a 30-day grace period, a 30-day usage window, and three confirmed uses. Automatic dreaming is disabled by default. `enabled=false` blocks active memory and both memory tools and prevents manual and scheduled dreaming; manual administration of persisted memories remains available. `automatic_dreaming_enabled=false` prevents only scheduled runs, while an explicit `Jetzt verarbeiten` remains available. `max_context_items` remains in the settings and API contract for compatibility but no longer limits context or has runtime effect.

Settings documents declare `global` or `user` scope. The `settings` table uses `user_id IS NULL` for global documents and a concrete `user_id` for user documents. Partial unique indexes enforce exactly one global document per key and one document per user and key. `SettingsStore` requires explicit scope and does not commit. `chat_sessions.user_id` connects the agent runtime and background processing to the correct memory settings even without an HTTP request.

## Memory Data Model

Memories have a current source (`manual`, `tool_call`, or `dreaming`), exactly one category (`context`, `fact`, `goal`, `identity`, or `preference`), a host-managed tier (`instant` or `retrieve`), an optional user tier lock, usage data, trust level, and persistent provenance. `instant` is active memory; `retrieve` is long-term memory available through RAG. Category describes the kind of knowledge, not its scope. A future project assignment is therefore a separate optional relation. `seen_at`, independent of `updated_at`, records whether the memory UI has displayed an automatically generated entry. Manual entries start seen; new tool and dreaming entries start unseen. Updates, deduplication, and additional evidence do not reset this state. Source messages are linked through `memory_source_messages`. A normalized SHA-256 hash is unique across all sources and categories. Normalization ignores case and whitespace differences. A database index and transactional savepoints preserve this invariant during concurrent writes. PostgreSQL stores `search_vector` as a persistent `to_tsvector('simple', ...)` column with a GIN index.

The memory service layer never commits. It provides CRUD, filtered and paginated full-text search, scope-filtered counts, and selection of complete active memories within the character budget. The local `memory_embeddings` table contains embeddings only for long-term memories and also serves as a persistent indexing queue. An embedding is valid only when its content hash and profile fingerprint match the current memory and active model contract. Moving a memory into active memory removes the embedding; moving it into long-term memory queues a new one. pgvector stores vectors in the same PostgreSQL database; there is no external vector database.

Infinity runs as an internal Docker service with the pinned `intfloat/multilingual-e5-small` model. Queries use the `query: ` prefix and memories use `passage: `. Public and private data share one local vector space. Separation happens in the database query: public runs filter to public memories before the top-K limit, while private runs can read both trust levels. Because content never leaves the local stack, request-scoped public pseudonymization is not applied to embeddings.

The embedding scheduler claims due entries with `FOR UPDATE SKIP LOCKED`, commits the claim before the HTTP call, and stores a result only if the content hash and profile are unchanged. Transient Infinity failures receive bounded backoff; structurally invalid responses are blocked with a safe error code. Memory writes remain independent. Startup requeues interrupted claims and missing or stale embeddings.

## Lifecycle and Usage

New and materially revised memories start in active memory unless a user lock fixes their tier. After memory, tier, and budget mutations, and before the first context build of a run, the host enforces `max_context_characters` under a transaction-wide capacity lock. This short maintenance transaction finishes before model access; read paths do not hold locks over external calls. All active memories are injected completely in stable order within the budget; there is no item limit or content truncation. On overflow, the host moves unlocked active memories to long-term memory in LRU order, based on last confirmed use, last tier change, and creation time. Locked active memories are never displaced; if they alone exceed the budget, the triggering settings, tier, or content mutation fails with `memory.tierBudgetExceeded`.

Only the user can lock a memory in active or long-term memory, or return it to automatic management, through `PATCH /api/memories/{id}`. Content, category, trust, and tier policy are stored in one transaction. The agent, `memory_write`, dreaming, and additional dreaming instructions never choose a tier. Releasing an active-memory lock restarts its grace period.

Injection into the system prompt or output through `memory_retrieve` creates only a persistent `pending` exposure in sessions with `memoryMode=full`; it is not proof of use. The exposure stores the exact shown memory content hash and final assistant answer. A later dreaming run must use `usedMemoryIds` to confirm exactly which memories materially contributed to that answer. The host marks all other exposures `unused`. Only confirmed `used` exposures for the current content count in the usage window and update `last_used_at`. Metadata-only and evidence-only revisions preserve this relation. `read_only` creates no exposures because that mode does not run dreaming attribution.

The dreaming scheduler evaluates tiering at most once per day when automatic dreaming is effectively available; manual dreaming also applies it. Unlocked active memories move to long-term memory after the grace period when they have fewer than `required_usage_count` confirmed uses in the usage window. Long-term memories return to active memory at that threshold, after which the character budget applies again. An exposure from a completed run that dreaming has not yet evaluated protects an active memory from demotion.

A real content revision deletes previous exposures and the last-used timestamp. An unlocked memory becomes active again; a lock keeps the selected tier. The revision also updates current source type, source session, source message, and run while preserving evidence links. Metadata-only changes and content differing only in case or whitespace preserve tier, usage, and current source. `sourceSession` therefore identifies the session of the current content revision but does not release its transcript. Provider references contain only the session ID; the authenticated administration API may also show the title. The agent must use `session_read` for details: the current session is host-allowed, while another source session requires the normal exact `session.read` permission or approval.

## Runtime Tools

The implicit storage rule applies only to stable self-context stated directly by the user in the latest user message. Facts found only in previous turns, assistant messages, memories, or tool results do not trigger a later implicit write; explicit storage requests may still refer to earlier statements.

`memory_write` stores or updates explicitly requested durable information and uncited stable self-context likely to be useful in later conversations. Such a first-person statement is an implicit storage request even without an explicit request to remember it, so the agent calls `memory_write` in the same turn. Examples include identity, origin, durable relationships, long-term goals, and stable preferences. Temporary situations, hypotheticals, quotations, and facts about third parties are not stored incidentally; independently changeable facts remain separate memories. Every write uses the normal session-bound `memory.write` permission with `allow_once`, `allow_session`, or `deny`; the host does not write without a matching grant. For creates, the model supplies only content and category; the host chooses the tier. Updates use a memory ID and monotonic revision already injected or read through `memory_retrieve`. After invalid arguments or a missing target, the model must retrieve the memory again instead of reusing the failed ID. The host reloads the target under a row lock and rejects stale updates with `memory.changed`. The host controls current revision source, session, assistant message, agent run, tool call, and trust level. Public models can update only public memories; private models can read and update both levels. If the model changes during an active request, read scope can only decrease while write classification remains bound to the model that generated the content. Private content can therefore never be persisted as public memory. Automatic updates can tighten trust only from `public` to `private`. The current assistant message is added as evidence. Exact create or update conflicts do not create duplicates and still receive the current evidence link. Tool arguments with large content remain persistently redacted; for model context, their preview is projected back as a schema-conforming string. The tool is independent of workspace write mode.

A lookup marked `purpose=write` or a nonterminal write starts a bounded host-controlled mutation workflow. Until completion, the runtime accepts only memory tools and discards final text drafts; only `stored`, `duplicate`, or `permission.denied` permits a controlled final answer. With multiple writes, an actually stored result takes precedence over an additional duplicate or denial. If an approved tool update exactly matches another memory, the host merges the stale target into the canonical memory: evidence and the stricter trust level remain, while the stale memory and obsolete embedding are removed. Manual updates retain their explicit duplicate error. Ineffective model-supplied IDs and revisions are discarded for creates. Canonical content remains limited to the user statement and is not enriched with geography or other model knowledge.

`memory_retrieve` requires an explicit `search` or `browse` mode and a `context` or `write` purpose. `search` combines only trust-filtered long-term memories from PostgreSQL FTS and cosine search through reciprocal rank fusion; lexical search remains available after Infinity or vector failures. `browse` lists all visible active and long-term memories by recency and does not run automatically after an unsuccessful search. Output includes purpose, mode, strategy, visible scope, total count, `hasMore`, and a stable `nextCursor` from `cursor_updated_at` and `cursor_id`. An empty result means only that nothing matched within that scope.

For normal user turns, the host adds exactly one automatic hybrid query over long-term memory to the complete active memory. Short follow-up questions include the preceding user turn in that query. At most three deduplicated RAG results with at most 2,500 content characters are injected. Semantic results require cosine distance at most `0.21`, a threshold bound to the pinned E5 profile. During Infinity failure only lexical matches remain. The host also computes scope-filtered counts once per run. This tells the model the available memory scope without sending all long-term memories every turn. `memory_retrieve` remains available for targeted hybrid search and browsing.

Explicit overview questions such as the German localized intent `Was weißt du über mich?` activate a host-controlled browse prefetch instead. The host injects at most 50 chronologically stable memories and 12,000 content characters without forcing a model tool loop. If more entries exist, it stores the keyset cursor `(updated_at, id)` internally on the assistant message; a matching localized follow-up continues from that cursor. Internal state is not sent to providers or exposed through the session API. `memory_retrieve` remains available for targeted searches and optional continuation. `session_search` searches chat transcripts only and does not replace persistent memory.

The tool continues to return ID, revision, category, tier, and current source session alongside content and trust. Automatic RAG results and active memories enter the system prompt with the same metadata and their injection source. Prompt injection and tool output record exposure, but only later dreaming attribution can confirm actual use. Results and prompt memories are explicitly marked untrusted. `memory_retrieve` is offered in `full` and `read_only`; `memory_write` only in `full`. Memory tool outputs are excluded from context summaries so private retrieval results cannot reach a public model through compaction. The administration API intentionally continues to use FTS and browse for stable counts and pagination.

## Dreaming

The internal scheduler starts and stops with the application lifespan. It processes only sessions in `full` mode with user memory and automatic dreaming enabled, no active agent run, and a stable user-assistant boundary. Manual runs require memory but not automatic dreaming. A blocked scheduled run can be queued again manually and therefore does not prevent explicit processing. Processing is incremental from the persisted checkpoint. `memory_dream_runs` stores status, trigger, source range, attempts, safe error codes, counters, and retry time; `memory_dream_states` stores the checkpoint and next scheduled time.

The dreaming model is `AiSettings.dreaming_model_id`, falling back to the default model. Tool support is the hard technical requirement. Reliable semantic extraction and reconciliation cannot be inferred from a model name or claimed parameter count; capable 26B-or-larger instruction models are recommended, while smaller models remain best effort and can use lower existing batch and candidate limits. Read scope for existing memories is the intersection of model release and evidence trust for the message batch: private memories are readable only when both model and batch are private. Existing private context therefore cannot influence a newly public-classified memory. A public dreaming model receives a private message batch either locally pseudonymized or deliberately unchanged according to the configured public policy. Dreaming uses a fixed host contract isolated from the general agent prompt. It includes source-message timestamps and trust-filtered active memory as explicitly untrusted reference context. Time-dependent statements should therefore be stored with their observation time rather than as timeless facts. Normal time and web-research instructions are not included.

Processing has up to two fixed model phases. First, the model returns structured candidates through `record_memory_candidates` from the message batch and trust-filtered active memories. For completed runs in the batch with pending exposures, it must also provide exactly one `usageAttributions` entry with the actually used `usedMemoryIds`. The host validates the configured candidate limit, evidence, exposed runs, and memory IDs after merging tool calls. It then finds exact, lexical, category-near, and optionally semantic existing memories for candidates. When matches exist, it sends the bounded match set and active memories to `reconcile_memory_candidates`; the model chooses `create`, `update`, or `unchanged` for each candidate through a schema bounded to the candidate count and index range. Multiple calls with the same tool name are merged into one domain result; after merging, the host requires exactly one attribution per exposed run and one decision per candidate. Contradictory or invalid output receives at most two repair attempts. Candidate extraction and reconciliation classify content and category, never tier. Normal `memory_write` is not offered; only the host writes after evidence, trust, revision, lifecycle, and deduplication checks. Optional `dreamingInstructions` add only extraction focus and categories and are never passed to reconciliation. Trust, tier, evidence, security, and deduplication remain host-controlled.

Dreaming defaults to an empty candidate list and stores only knowledge likely to remain useful across sessions: stable identity, durable relationships, explicit recurring preferences, long-term goals, and concrete ongoing projects. The model must call `record_memory_candidates` even when that list is empty. One-off searches, shopping or restaurant requests, media or image requests, translations, temporary curiosity, and a single request that merely suggests an interest or preference are not memories. Every candidate must cite at least one user message from the batch; assistant messages may supplement evidence but can never be its sole support. Existing memories are reference data rather than evidence, and extraction must not emit broader, weaker, or paraphrased copies of an existing memory or another candidate. Canonical memories remain atomic and in the source language.

For nonempty candidates, the host combines active and retrieved long-term memories seen during extraction with a bounded trust-filtered set of exact, lexically similar, semantically similar, and same-category memories. Candidates are embedded together locally; lexical reconciliation remains available when Infinity fails. A second isolated and repairable model request chooses `unchanged` when an existing memory already covers a candidate or is more specific, `update` only for a correction or material refinement of the same proposition or ongoing goal, and `create` only for an independent durable proposition. A related topic alone never justifies combining memories, and facts that can change independently remain separate. The model may reference only supplied memory IDs and must not strengthen uncertainty. Updates replace canonical content and reclassify category. A content revision resets usage and automatic tier and adopts the dreaming session as current source; seen state and accumulated evidence remain.

Dreaming memories conservatively inherit the highest trust level in the processed message batch. Exact-content deduplication applies across trust levels; `private` wins a conflict and new evidence links merge into the existing memory. An update whose target content already belongs to another memory remains unchanged. Dreaming runs count created and updated memories separately. Empty candidate lists succeed. Failures do not advance the checkpoint and use bounded retries with backoff.

Backend startup requeues previously running dreaming jobs below their maximum attempt count; exhausted jobs finish safely as failed. Jobs blocked by unavailable or policy-disabled model configuration retain their source range and can be requeued after configuration changes. A failed run must not block the scheduler permanently. Dreaming transfers no reasoning or provider data, normal agent tool output, or binary content.

## API

The authenticated `/api/memories` router provides CRUD, paginated filter and FTS search including category and tier filters, user-scoped memory settings, and owner-filtered dreaming runs. Create accepts content, category, and trust; new memories start in host-controlled active memory. Update also requires `tierPolicy` with `automatic`, `fixed_instant`, or `fixed_retrieve` and stores it atomically with other changes. Memory payloads include `retrievalLevel`, `tierLocked`, `tierChangedAt`, `lastUsedAt`, confirmed `usageCount` for the configured window, and `sourceSession`. Settings accept and return `maxContextCharacters`, `shortTermGraceDays`, `usageWindowDays`, and `requiredUsageCount`; `maxContextItems` is carried only for compatibility. After rendering a list page, the UI acknowledges its unseen IDs in one `POST /api/memories/acknowledgements` call; filtering and pagination do not mark undisplayed entries. Manual create and update conflicts return `409 memory.duplicate`; an impossible lock budget returns `409 memory.tierBudgetExceeded`. Settings updates are partial PATCH operations, so toggles do not save unconfirmed technical form values. JSON fields use camelCase. Errors use only stable codes from the central error contract; provider responses and exception text never reach clients.

## Future Multiuser Extension

This stage intentionally remains single-user. Sessions, memory settings, user preferences, and dreaming runs already have technical user ownership. Persisted memories, search, and cross-source deduplication remain installation-wide and require a binding ownership boundary before additional accounts are added. `public` and `private` remain model data-release levels and must not be treated as user permissions.

Existing service boundaries remain the intended integration points: `MemoryService` encapsulates memory queries, and `DreamingService` encapsulates the queue and checkpoints. A future migration must add at least owner-scoped CRUD and FTS queries, owner-scoped dreaming deduplication, and separate normal and administrative APIs. The scheduler must then distribute jobs fairly between users; multiple backend workers also require leases instead of global startup recovery.
