# Protected text in tools

`secret_input` returns run- or session-scoped value references. A tool data field that accepts `ProtectedText` can combine literal parts with `{ "value_ref": "run-secret:..." }` parts, for example `{ "parts": ["prefix=", { "value_ref": "run-secret:<id>" }] }`. The backend resolves those parts only in the tool handler, after any field-specific authorization, and validates the assembled value against the normal size and content limits. Target paths, resource selectors, authorization scopes, and tool results are not generic substitution surfaces. Tool implementations must explicitly opt data fields into this shared type; adding the type does not authorize external delivery or durable storage of a credential.

File tools separate ordinary text from protected text. `write_file` takes exactly one of `content` (a string, including serialized JSON) and `protected_content` (`ProtectedText`). `edit_file` takes exactly one of `oldString` and `protected_oldString`, and exactly one of `newString` and `protected_newString`. Empty replacement strings are valid; empty search strings are not. Both forms use the same permission checks and file operation. Protected values are assembled only after authorization and then checked against the ordinary text limits.

Previously stored protected objects under `content`, `oldString`, or `newString` remain accepted internally, without changing the original arguments or their approval binding. They are not advertised in the new schemas. A plain JSON object is not implicitly serialized into file content. Changed tool schemas intentionally invalidate the reusable prompt prefix once; persisted historical tool calls remain unchanged.

`generate_qr_code.content` accepts protected text. `generate_qr_code.wifi` also accepts separate protected SSID, password, and security fields; the host validates the security type and escapes the Wi-Fi payload. QR PNGs containing protected values are user-visible artifacts but are excluded from automatic model image input and `read_qr_code` output. Argument history stores redacted QR content and protected file content, never assembled plaintext. Run-only references expire at the end of the run; session reuse still requires the user's opt-in.
